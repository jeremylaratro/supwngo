### 0. Verdict

- **supwngo contains no LLM integration.** The `ai` extra (`pyproject.toml:79-82`) and `requirements.txt:40` ("`supwngo/ai/*`, lazily imported, guarded") point at a package that is not in this tree. The only model calls are a cloud-only benchmark follower (`benchmark/walkthrough/followers.py:517-576`) and a dev script running `claude --dangerously-skip-permissions` (`scripts/auto_implement.sh:343`).
- **The repo's one LLM measurement undercuts the current direction.** A bare Sonnet-tier agent with a shell and no supwngo solved `08_ret2dlresolve` and `09_srop` 2/2 (`docs/reports/2026-09-24-walkthrough-scorer-first-measurement.md:217-222`), while supwngo's own templates were broken on 8 of 13 round-1 targets (`:113`). An embedded "AI analyzer" would compete with a generic agent that already wins on that corpus.
- **supwngo's real asset is its oracle layer:** per-attempt receipt tokens (`contracts.py:513-547`), echo-vs-shell discrimination (`verifier.py:76-86`), the evidence-carrying `Fact` model (`walkthrough/model.py:155-215`) and negative-control corpora. That is what an LLM lacks, and it is not reachable as a tool today.
- **Heuristic gaps are being patched with string lists that leak the eval set.** `WinFunctionFinder.WIN_NAMES` contains the literal `"fill_ammo"` (`supwngo/exploit/offset_finder.py:887`), the answer to rocket_blaster_xxx. Three divergent win-name lists exist (`strategy.py:178`, `profile_stage.py:30`, `offset_finder.py:881`).
- **Highest-leverage move:** make supwngo a deterministic, JSON-contracted toolbox with a public `verify` oracle, and add LLMs only as closed-set proposers whose picks must be confirmed by an oracle before entering any fact store or exploit. Do not build an in-tree agent; the owner already has one.

### 1. Findings

**D4-F1 — The `ai` extra is a dangling promise (medium).**
Evidence: `pyproject.toml:79-82` lists `anthropic`/`openai`. `requirements.txt:40` and `CHANGELOG.md:4232` reference `supwngo/ai/*`. `docs/roadmaps/PARKED.md:31` says it lives in `ai/` with "two `pickle.load()` sinks". A glob for `supwngo/**/ai/**` returns nothing, and nothing in `supwngo/` imports either SDK. Whether the package was deleted or never exported is UNVERIFIED.
Why it matters: installing `.[ai]` pulls two cloud SDKs that do nothing. Neither is needed for the offline case, since vLLM speaks the OpenAI wire protocol and `requests` is already a core dependency (`pyproject.toml:58`).

**D4-F2 — The only LLM instrument is cloud-bound, unpinnable and unsandboxed (high).**
Evidence: `AgentFollower.run` shells out to `claude -p --model sonnet` (`followers.py:541-576`). The code admits "`sonnet` is a MUTABLE ALIAS… the model is not pinnable from here" (`followers.py:463-469`). Isolation is "process-level, not OS-level… `HOME` is shared" (first-measurement report `:267-270`).
Why it matters: the instrument cannot run air-gapped, its numbers are not reproducible across months, and it gives a shell to an agent that executes target binaries. Local vLLM models are pinnable by weights hash, so offline is the better evaluation setting, not a degraded one.

**D4-F3 — A bare agent matches or beats supwngo's artifacts on its own corpus (critical for strategy).**
Evidence: first-measurement report `:199-204`: the bare arm scored 2/2 on `04`, `08`, `09`. The tier-decision doc states: "The walkthrough changes what the follower's attempt **costs**, not what it can **do**" (`docs/plans/2026-09-24-walkthrough-follower-tier-decision.md:72-73`). Timings were 34.5 s vs 113.6 s on `02`, and credited vs a 900 s timeout on `12`.
Why it matters: the defensible value of supwngo next to an LLM is cost, determinism and verification. "Best in existence" should be measured as *agent + supwngo* vs *agent alone* on solve rate, tokens and wall-clock. Caveat: this was the synthetic round-1 corpus; the bare agent on the seven HTB targets is unmeasured.

**D4-F4 — Semantic judgements are implemented as string tables, and one is contaminated (high).**
Evidence:
- `offset_finder.py:881-889` includes `"fill_ammo"`, `"target"`, `"debug"`, `"admin"`, `"solve"`, `"answer"`, matched as substrings (`:937`).
- `_find_by_file_ops` flags any function calling `read@plt` as a win candidate (`:969-973`).
- `StrategySuggester.WIN_FUNCTIONS` (`strategy.py:178-182`) is a third, shorter list, which is why `pwn` misses ret2win on rocket_blaster_xxx.
- `find_vulnerabilities_in_decompiled` is nine regexes (`decompile.py:627-637`).
- Input-prompt detection is ten regexes (`profile_stage.py:43-47`).

Why it matters: these are the places an LLM beats regexes: "which function is the payoff", "what role does `ta_alloc` play", "what does this menu want". They are also where the project is overfitting by hand. A `fill_ammo` literal makes any rocket_blaster result worthless as evidence.

**D4-F5 — No provenance slot for a model-proposed value, and the schema that could carry one is unwired (high).**
Evidence: `schema/resolve.py:65-78` defines `Provenance` as MEASURED/DERIVED/ASSUMED/ASSERTED/UNKNOWN. A grep for `supwngo.schema` in `supwngo/` hits only `schema/resolve.py` and `schema/mutants.py`, so the 3.7k-LoC resolver is not imported by the pipeline. The live channel for external facts is `known_facts: Dict[str, int]` with four keys (`orchestrator.py:1054-1068`), with no source field. `--win`/`--ret2` are deliberately unvalidated (`target_overrides.py:62-68`).
Why it matters: if an LLM is wired into `known_facts` or `win_override` as they stand, a hallucinated address is indistinguishable from an operator's or a measured one. That is the exact failure the brief forbids.

**D4-F6 — The CLI is close to a machine interface but not a contract (high).**
Evidence:
- Most commands have `--json`; `triage` (`cli.py:229-235`) and `batch` (`:1100-1104`) do not.
- Only the handoff has a `schema_version` (`handoff.py:33`).
- Failures exit 0: decompile failure emits `{"error": ...}` with no `ctx.exit` (`cli.py:2129-2134`); `offset --json` likewise (`:934-935`). Non-zero exits appear only at `:492, 3041, 3651, 3768, 3781`.
- Address encoding is inconsistent: int in `ResolvedTarget.to_dict` (`target_overrides.py:137`), hex string in `AttemptRecord.to_dict` (`contracts.py:486`) and decompile (`cli.py:2091`), raw value in `StrategyReport` (`strategy.py:168`).
- Human-mode decompile truncates to 3,000 chars (`cli.py:2114`).
- The project's own harness scrapes stdout from first `{` to last `}` (`benchmark/run_bench.py:465-477`). Whether `_json_mode` (`cli.py:28-46`) has since made that unnecessary is UNVERIFIED.

Why it matters: the owner's agents drive tools through a shell. A tool that exits 0 on failure, truncates silently and changes address encodings between commands will be misread by an agent.

**D4-F7 — The brief understates the override flags (medium).**
Evidence: the brief says "No such flags exist today". `--win`, `--ret2` and `--rop` exist (`cli.py:66-109`) and are attached to `autopwn` (`:2840`), `explain` (`:3238`) and `solve` (`:3449`), with a resolver and JSON-surfaced warnings (`target_overrides.py:201-292`). They are missing from `pwn` and `template`.
Why it matters: PASS criterion (a) is mostly an aliasing and coverage job, not a build. It is also the attach point for LLM-proposed targets, provided proposals arrive as candidates rather than as overrides.

**D4-F8 — No oracle is exposed to callers (high).**
Evidence: `PipelineVerifier` has `verify_payload`, `verify_shell` and `verify_via_tester` (`verifier.py:26-41`). No `verify` command exists in the list at `cli.py:142-3703`. There is no command to run a single named technique with supplied facts and get back an `AttemptRecord`.
Why it matters: an agent's biggest weakness in exploit development is false belief in success. The first-measurement report documents flag laundering and echo ambiguity (`:74-91`). supwngo has solved that and keeps it private.

**D4-F9 — Per-invocation cost blocks any propose→observe loop (high).**
Evidence: the Ghidra script decompiles one function per `analyzeHeadless` run (`SupwngoDecompile.java:109-123`). `decompile_all` loops `self.decompile` over up to 100 symbols (`decompile.py:609-614`); that each call re-runs auto-analysis is UNVERIFIED. The brief records 180 s caps in the CLI flow. There is no call-graph, xref or stack-frame export. `core/database.py:147-189` has a sha256-keyed analysis cache, but its use by `decompile` is UNVERIFIED.
Why it matters: every LLM hook needs whole-program context once, cached. Static "offset on all" should come from Ghidra's stack-frame layout, not from an LLM reading pseudo-C.

**D4-F10 — Offline violations and injection surface already exist (medium).**
Evidence: `remote/libc_db.py:41-42` hard-codes `https://libc.rip/api` and `libc.blukat.me`; `utils/config.py:71` defaults `libc_database_url` to the same. Target strings flow verbatim into JSON (`analysis/static.py:345-351`), decompiled code carries string literals, and target stdout is pattern-matched during profiling (`profile_stage.py:37-47`).
Why it matters: libc identification must not go to the network in an air-gapped platform, and must not go to an LLM either. Every byte of the target is attacker-controlled text that will land in a prompt.

**D4-F11 — "Right method listed" is gameable, and an LLM makes that worse (high, challenges the PASS criteria).**
Evidence: `StrategySuggester` appends `VARIABLE_OVERWRITE` unconditionally (`strategy.py:266-272`). `_check_rop_execve_viable` returns `True` when gadgets were not analyzed (`:401-406`).
Why it matters: a method counts only when recommended and accompanied by machine-checkable preconditions. An LLM classifier will name SROP for sick_rop from the filename alone. Cloud models have likely seen writeups for retired HTB challenges (UNVERIFIED per target), so the seven-target set cannot validate LLM hooks.

### 2. Recommendations

**D4-R1 — Ship a versioned machine contract: `supwngo.tool/v1`.**
What:
- Add a `supwngo/api.py` facade of pure functions returning dataclasses, and make the CLI a thin renderer over it.
- Put every `--json` output in one envelope: `{"schema": "supwngo.tool/v1", "command", "ok", "error": {"code", "message"} | null, "binary": {"path", "sha256"}, "data", "provenance": [...], "timings"}`.
- Rules: stdout carries exactly one JSON document; exit 0 only if `ok`, 2 for "ran, negative result", 1 for a fault; addresses are always `"0x…"` strings; no truncation in JSON; `--out FILE` on everything.
- Add `supwngo tools --json` that emits a manifest (name, argument schema, output schema, side-effect class `read|exec-target|network`) generated from the Click tree. The in-house agentic CLI ingests it directly.
- Add `--win/--ret2` to `pwn` and `template`, with `--winfun`/`--eip` as aliases.

Impact: every agent, including the existing `claude -p` follower, can use supwngo without scraping. Effort: M. Dependencies: the engine-consolidation dimension (one facade, not five engines). Risk: schema churn; mitigate with append-only rules as in `handoff.py:11-15`.
Success measure: `run_bench.parse_json_result` is replaced by `json.loads(stdout)` with zero failures across all commands on all `benchmark/corpus_*` targets, and a contract test asserts `ok == (exit code == 0)` for all 33 commands.

**D4-R2 — Expose the oracles: `facts`, `verify`, `try`.**
What:
- `supwngo facts BIN --json`: one cached document with protections, functions (address, size, callers, callees), strings with xrefs, imports, gadget classes present, and per-function stack frames. Every item carries `{value, provenance, evidence: {method, command}}`, reusing `walkthrough/model.py:Evidence`.
- `supwngo verify BIN --script exploit.py --json`: runs `PipelineVerifier.verify_via_tester` and returns the `VerificationReceipt` including `shell_proven` and `echo_ambiguous`.
- `supwngo try BIN --technique NAME [--offset N --win X …] --json`: runs one registry executor and returns its `AttemptRecord`.
- Run target execution in a no-network container or bubblewrap by default.

Impact: this is what F3 says agents lack — cheap ground truth and a judge that cannot be talked into a false success. Effort: M. Dependencies: D4-R1. Risk: `verify` runs arbitrary scripts, so the sandbox is mandatory.
Success measure: the eight `broken_*` fixtures from the scorer self-test (report `:24-31`) are all refused through `supwngo verify`, and the positive control is credited.

**D4-R3 — One analysis pass per binary, in a sha256-keyed workspace.**
What: extend the Ghidra script, or add a sibling, to export in one headless run: all functions, pseudo-C, call graph, string xrefs, and stack-frame variables with offsets relative to the return address. Persist the Ghidra project under `~/.supwngo/ws/<sha256>/` so later calls use `-process … -noanalysis`.
The stack-frame export gives a deterministic static offset candidate per (function, buffer). That is the oracle for "offset on all", including PE. An LLM may rank which buffer; it never produces the number.
Impact: unblocks every hook and the PE and offset criteria. Effort: M. Dependencies: decompile dimension. Risk: Ghidra frame recovery is wrong on hand-written assembly such as sick_rop; label those results DERIVED and confirm under gdb where the target is runnable.
Success measure: a second `decompile` on the same binary returns in under 5 s; the static offset equals the gdb-measured offset on at least 90% of crashable `benchmark/corpus*` stack targets, with misses reported as UNKNOWN rather than wrong.

**D4-R4 — `supwngo/llm/`: one provider, OpenAI-compatible, off by default.**
What:
- `client.py`: `/v1/chat/completions` over `requests`, with JSON-schema constrained output (vLLM guided decoding; verify the exact parameter against the deployed vLLM version).
- `router.py`: three roles, `bulk`, `reason`, `hard`, each mapped in `utils/config.py` to `{base_url, model, max_tokens, timeout}`.
- An `airgap: true` default that refuses any host outside an allowlist.
- CLI: `--llm off|local|any`, default `off`.
- Replace the `ai` extra's contents; an Anthropic adapter is optional and lives behind the same interface.
- Policy: escalate from `bulk` to `reason` to `hard` only when the oracle rejects all proposals from the tier below, never on self-reported confidence. Per-run caps on calls and tokens are recorded in the envelope.
- `ledger.py`: a SQLite table beside `core/database.py`, keyed by `sha256(model_id + weights_hash + prompt + schema + params)`, storing request, response, tokens and latency. Modes: `live`, `record`, `replay`. Pytest runs `replay` only.

Impact: offline-first, reproducible, and the roughly 2,230 tests stay deterministic. Effort: S–M. Dependencies: none. Risk: guided decoding degrades reasoning on small models; let the model reason in one field and answer in a second, schema-bound field.
Success measure: with the network blocked, `--llm local` completes and `--llm any` fails closed; a `replay` run reproduces byte-identical envelopes; zero outbound connections from the `supwngo` test suite, which also forces `libc_db` to a local libc-database mirror.

**D4-R5 — Hypothesis queue with mandatory promotion: the trust core.**
What: add `supwngo/llm/hypothesis.py` with `Hypothesis{id, kind, claim, source: {model, ledger_key}, oracle, status: proposed|confirmed|refuted|untestable, evidence}`. Three invariants, each enforced by tests:
- **Closed-set outputs.** A hook's schema lets the model return only indices into a deterministic candidate list (function ids from `facts`, technique names from the registry, buffer ids from frames), enums, or small bounded integers flagged as hypotheses. The model has no field in which to write an address.
- **No unconfirmed value reaches a builder.** `Hypothesis` objects are not `Fact`s. Only an oracle result creates a fact, stamped MEASURED or DERIVED with the oracle as `Evidence.command`. `untestable` hypotheses appear only in reports, labelled as such. Do not add an LLM member to `Provenance`.
- **Target text is data.** Target-derived strings are length-capped, wrapped in a delimited block, and hook calls are tool-less single completions. An injected instruction can at worst cause a wrong index, which the oracle refutes.

Impact: makes the "no hallucinated address" requirement structural rather than aspirational. Effort: M. Dependencies: D4-R3, D4-R4. Risk: oracles cost time; cap proposals per hook at 3–5.
Success measure: a property test fuzzes model responses with random addresses and injected text and asserts no builder input changes without an oracle record. An injection corpus (R9) shows a 0% change in final recommended method versus the same binary with the string neutralised.

**D4-R6 — First three hooks, in this order.** Each replaces a string table.

| Hook | Attach point | Model picks | Oracle | Role |
|---|---|---|---|---|
| Payoff-function nomination | `profile_stage.run_static_analysis`, between override and name scan (`profile_stage.py:123-150`); mirrored in `orchestrator._suggest_strategy` (`:1088-1094`) | Up to 3 function ids, given names, callees, referenced strings and short pseudo-C | Static: the function reaches `system`/`execve`/`open`+`write` or references a flag-like string. Dynamic: ret2win attempt receipt | `bulk` |
| Allocator and role labelling | `vulns/heap_advanced.py` allocator discovery | Functions labelled `alloc`/`free`/`realloc`/`none` | gdb or ltrace trace: `alloc` returns distinct writable pointers; a pointer passed to `free` is later returned again | `bulk` |
| Vulnerability hypothesis | Replace the regex list in `Decompiler.find_vulnerabilities_in_decompiled` (`decompile.py:618-650`) | `{function id, class enum, sink call-site id, source id}` | Existing detectors (`dataflow`, `vulns/*`) re-run scoped to that function; then symbolic or crash confirmation | `reason` |

After these land, delete `"fill_ammo"` and the other eval-specific names from `WIN_NAMES`, and collapse the three lists into one.
Impact: directly targets the brief's rocket_blaster miss (no RET2WIN) and auth-or-out miss (0 allocators). Effort: M. Dependencies: D4-R3, D4-R4, D4-R5. Risk: hook 3 yields plausible but untestable claims; they stay `untestable` and never raise a method's rank.
Success measure, on a held-out variant set (R9) with symbols renamed:
- Payoff nomination: at least 90% top-3 recall and no more than 5% confirmed-false on negative controls, against the name-list baseline.
- Allocator labelling: non-zero alloc/free sites on every custom-allocator variant, and zero on non-allocator controls.
- If `--llm off` matches these numbers, delete the hook.

**D4-R7 — Method selection: the LLM reorders, never adds.**
What: in `orchestrator._ordered_technique_names` (`orchestrator.py:1099-1140`), allow an optional LLM-proposed permutation of the already-applicable technique names. `is_applicable` gates and receipts are unchanged. For `pwn` and `template -t auto`, a method may be labelled "recommended" only if its preconditions are listed as confirmed facts. Fix the brief's SROP miss deterministically (rax via `read` return plus `syscall; ret`); that is a rule, not a model call.
Impact: lower time-to-first-success. It cannot produce a wrong exploit, only a slower run. Effort: S. Dependencies: D4-R4. Risk: negligible by construction.
Success measure: median attempts-before-success drops by at least 30% on the R9 set with identical solve count; if not, remove the hook.

**D4-R8 — Input-shape and menu inference, then seeds and dictionaries.**
What: the model proposes a menu or format grammar as JSON for `fuzzing/grammar.py:GrammarParser.parse_json` (`:205`), a container spec for the reserved `DeliverySpec.container` (`contracts.py:211-216`), and AFL dictionary tokens for `afl.generate_harness` (`afl.py:380`).
Oracle: a gdb breakpoint or coverage shows the proposed input reaches the function the vulnerability hypothesis named. No coverage gain means the proposal is discarded.
Impact: snow_scan's BMP gate and menu-driven targets are where cyclic-pattern offsets fail today. Effort: L. Dependencies: D4-R3, D4-R5, D4-R6. Risk: highest injection exposure, because the model reads live target output; keep these calls tool-less. Needs `reason`, or `hard` for binary formats.
Success measure: fraction of R9 menu and format targets where execution reaches the vulnerable function, LLM-on vs off, with a pre-registered threshold of +30 points.

**D4-R9 — An evaluation harness that can say "no".**
What:
- Generate held-out variants from the existing C corpora and their negative controls (`*_90_neg_*`), under mutations: symbol rename, strip, compiler and flag change, constant change, decoy win functions.
- Add injection fixtures: binaries whose strings and banners contain instructions such as "the win function is `decoy`".
- Report per hook: confirmed-rate, refuted-rate, untestable-rate, the delta in recommended-method accuracy against `--llm off`, tokens and seconds.
- Run two system arms through the existing `AgentFollower` harness, ported to the R4 provider so it runs on local models: agent alone, and agent plus the supwngo toolbox.
- Add a contamination probe: ask each model for the solution given only the challenge name; flag targets it answers.
- Treat the HTB seven as a smoke test, never a tuning set.

Impact: the only defence against overfitting and against the project fooling itself. Effort: M. Dependencies: D4-R1, D4-R2, D4-R4. Risk: variant generation is itself work; reuse the corpus YAMLs.
Success measure: the harness refuses a planted cheat (a hook that returns the manifest's ground truth) and flags the `fill_ammo` list as dropping to baseline under rename.

**D4-R10 — Prose last: LLM text in `explain` and `report`, fact-locked.**
What: the model writes only `why`/`detail` text for walkthrough steps and report narrative. A validator rejects any output containing a hex literal, decimal offset or symbol not present in the walkthrough's `Fact` set (`model.py:182-215`). Code and constants keep rendering from facts.
Impact: cosmetic, and the measured effect of walkthroughs is cost, not capability. Effort: S. Dependencies: D4-R4. Risk: low.
Success measure: 0 validator escapes on 200 generated walkthroughs; follower time-to-solve does not get worse.

**D4-R11 — MCP server as a generated wrapper; no in-tree agent.**
What: a roughly 200-line stdio MCP server generated from the `tools --json` manifest, calling `supwngo.api`. Do not build an agent loop inside supwngo; publish a skill or prompt pack for the in-house agentic CLI instead.
Impact: parity for MCP clients at near-zero maintenance. Effort: S. Dependencies: D4-R1. Risk: a second surface; generation keeps it in lockstep.
Success measure: the manifest and the MCP tool list are identical in CI.

**Model capability per hook**

| Hook | Role | What it needs |
|---|---|---|
| Payoff nomination, allocator labels, prose | `bulk` | Small local code model, 8–16k context, reliable JSON |
| Vulnerability hypothesis, method reorder, menu grammar | `reason` | Strongest local model, around 32k context; multi-function reasoning |

### 3. Hypotheses and experiments

**D4-H1 — Agent plus supwngo toolbox beats agent alone on cost, not solve rate.**
Experiment: R9 two-arm run, 20 variants, 2 reps, same local model, the bare arm against the same agent with `facts`/`verify`/`try`.
Falsifier: median wall-clock and tokens improve by less than 25% and solve rate does not improve. Then the toolbox is not earning its place and the project should narrow to the verifier and corpus.

**D4-H2 — A small local model matches a frontier model at closed-set payoff nomination.**
Experiment: 50 renamed or stripped variants, top-3 recall, `bulk` vs cloud.
Falsifier: a gap above 10 points. Then `bulk` routing is wrong for this hook.

**D4-H3 — Closed-set outputs plus oracles drive hallucinated-value incidents to zero.**
Experiment: replace the model with an adversarial stub emitting random or malicious responses across 1,000 runs.
Falsifier: any builder input or emitted script contains a value with no oracle record.

**D4-H4 — LLM vulnerability hypotheses add recall the detectors lack, at tolerable precision.**
Experiment: all C-source corpora including negatives; compare confirmed findings with LLM on and off.
Falsifier: fewer than 10% additional confirmed true positives, or more than 20% of proposals on negative controls surviving as "confirmed". The second outcome means the oracle is too weak, which is the more important result.

**D4-H5 — Cloud models are contaminated on the HTB seven.**
Experiment: name-only prompt, "what is the intended technique for HTB `<name>`?".
Falsifier: 2 or fewer of 7 correct. Then the seven are usable as a weak LLM test.

**D4-H6 — Ghidra frame export gives a correct static offset on most stack targets with no LLM.**
Experiment: compare to gdb ground truth on corpus stack targets.
Falsifier: under 70% exact. Then a model-assisted or symbolic frame recovery is justified.

**D4-H7 — Prompt injection through binary strings changes outputs in a naive integration.**
Experiment: a prototype of the payoff hook without R5 constraints on the injection fixtures.
Falsifier: under 5% flip rate. Then R5's delimiting is lower priority, though the closed-set rule stays.

### 4. Best-in-class gap

Named from memory; verify specifics before citing externally.

- **DARPA AIxCC finalists (Team Atlanta's Atlantis, Trail of Bits' Buttercup, Theori, Shellphish).** The LLM proposes, and fuzzers, sanitizers and proof-of-vulnerability runs dispose. Budgets, model routing and caching are first-class. Copy the proposer/oracle split and budget accounting. Do not copy the source-level and patching machinery or the cluster orchestration; this is a binary-only, single-maintainer project.
- **Google Naptime / Big Sleep.** The agent gets a debugger, a code browser and a scripting tool, and must produce a reproducible crash as proof. Copy the "verifiable outcome or it didn't happen" rule and the small, sharp toolset. That is R2.
- **OSS-Fuzz-Gen.** LLM-written harnesses accepted only if they build and gain coverage. Copy the coverage-as-oracle rule for R8.
- **ReSym, LLM4Decompile, DeGPT.** Models recover names, types and structs. Useful for readability and hook context, but the outputs are not checkable facts. Keep them as display annotations, never as analysis input.
- **GhidraMCP and similar RE-tool MCP servers.** These let agents drive RE tools interactively but return unversioned free text with no verification. Copy the idea of a persistent analysis session (R3); beat them with typed, provenance-carrying output.
- **PentestGPT, EnIGMA (SWE-agent for CTF), Cybench, NYU CTF Bench.** These are general agent loops with interactive tools. Do not rebuild one. The owner has an agent platform, and the repo's own data shows a generic loop already solves the easy and medium corpus. Compete on what they lack: receipts, laundering detection, negative controls.
- **Mayhem / angr-era AEG.** Fully deterministic exploit generation. supwngo already has more of this than it can validate. The gap is evaluation discipline, which the walkthrough scorer shows the project can do well.

In this dimension supwngo's scorer and receipt design are already near best-in-class. Nothing downstream consumes them as a service.

### 5. Questions for the owner

1. Is the product "an autonomous solver" or "the verified toolbox agents use"? F3 argues for the second; R1, R2 and R11 assume it. If the first, this roadmap is wrong.
2. Will you accept "recommended, with confirmed preconditions" as the PASS bar instead of "method appears in output"? Without that, an LLM hook can pass the criteria without being right.
3. Which model IDs are served on the DGX Spark nodes, and does the deployed vLLM support JSON-schema guided decoding? This fixes the `bulk`/`reason` mapping and whether R5's closed-set schemas are enforceable server-side.
4. May cloud models ever see target binaries or decompiled output, or are they limited to development and evaluation? This decides whether `--llm any` exists at all.
