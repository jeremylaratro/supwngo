# Dimension D1 — Architecture, scalability and maintainability (adversarial)

Your dimension: is supwngo built so it can grow into the best automated binary RE/VR tool, or is it
collapsing under its own weight? Scope:
- **Engine sprawl.** At least five overlapping decision engines (`pwn`/StrategySuggester in
  `supwngo/exploit/strategy.py`; `autopwn`/`solve` canonical pipeline under `supwngo/exploit/pipeline/`;
  legacy `exploit --auto` in top-level `supwngo/exploit/*.py`; `explain` walkthrough in
  `supwngo/exploit/walkthrough/`; `template`). Map them, show where they duplicate or contradict each
  other, and propose a target architecture (single source of truth for facts → method → artefact).
- **Module boundaries and the data model.** `supwngo/core/` (Binary, ExploitContext, database),
  `supwngo/schema/`, how facts flow between analysis, detection and exploitation; whether analyses are
  cached / reusable / composable; the plugin model (or lack of one) for detectors, techniques, formats
  (ELF today, PE wanted) and architectures.
- **Scalability.** Batch/corpus-scale runs, concurrency, budgets and timeouts (angr in a killed
  subprocess, Ghidra headless), caching, determinism, resource isolation, running many targets on a
  small cluster.
- **Maintainability.** `supwngo/cli.py` (3.9k lines), the 102k-LoC `exploit/` package, dead code,
  test architecture (`tests/`, ~2,230 tests, no CI runner), packaging.
- Read `docs/architecture/`, `docs/adr/`, `docs/roadmaps/` and say where existing plans are right,
  stale, or wrong.
Use `D1` as the ID prefix.
