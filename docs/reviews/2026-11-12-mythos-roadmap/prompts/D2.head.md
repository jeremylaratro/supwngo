# Dimension D2 — Reverse-engineering and vulnerability-discovery depth (adversarial)

Your dimension: how good is supwngo at *understanding* a binary and *finding* the bug, compared with
the state of the art? Scope:
- **Analysis stack.** `supwngo/analysis/` (static, dynamic, protections, cfg, dataflow, strings,
  decompile — Ghidra headless via `analysis/ghidra_scripts/SupwngoDecompile.java` with angr fallback),
  `supwngo/symbolic/` (angr), `supwngo/fuzzing/` (AFL++, honggfuzz, libFuzzer wrappers, crash triage).
  How deep, how correct, how robust (timeouts, stripped/static binaries, no `main`).
- **Detection.** `supwngo/vulns/` (stack BOF, heap, `heap_advanced.py`, format string, integer, …)
  and the `report` command. Today `report` finds 0 findings on three targets with known bugs, and the
  heap analyser is blind to in-binary allocators. Diagnose the detection *approach* (name/pattern
  matching vs data-flow vs symbolic vs dynamic evidence) and its precision/recall problem, not just the
  instances.
- **Formats and architectures.** ELF x86-64 today; PE requested now; what about x86, ARM/AArch64,
  MIPS, Mach-O, firmware, kernel (`supwngo/kernel/`)?
- **Tools to add.** Evaluate concretely: Ghidra (PyGhidra / Ghidra-as-a-library, BSim, Version
  Tracking), rizin/radare2, Binary Ninja headless, IDA, RetDec, BAP, Triton, angr features not used,
  Qiling/Unicorn emulation, wine for PE dynamic runs, LibAFL, AFL++ QEMU/frida mode, honggfuzz,
  symbolic-concolic hybrids (SymCC/SymQEMU), sanitiser-instrumented rebuilds, binary lifters
  (e.g. to LLVM IR or P-code), diffing (BinDiff/Diaphora) for patch-diff VR, function-signature
  libraries (FLIRT/FLIRT-like, Ghidra function ID) for stripped static binaries.
- Compare with CGC-era cyber-reasoning systems (Mayhem, Mechanical Phish/angr, Xandra), AIxCC-era
  LLM-plus-fuzzing systems, and LLM-assisted VR work (e.g. Big Sleep). Say what is genuinely
  transferable to a single-maintainer, offline-first tool.
Use `D2` as the ID prefix.
