## Revision history

- **v1 — REJECTED** by two independent reviewers who converged on the same
  verdict and the same primary fix.
  - Fatal flaw: `ExploitContext` was to be *the* serialized model, with a
    lossless round-trip, without new import edges. The code permits at
    most one of those three.
  - The merge layer — which v1 itself called "the part most likely to be
    got wrong" — was undefined for its own headline use case (7 of 16
    provenance cells missing, including **every** cell where the incoming
    fact is `asserted`) and failed open on the strongest signal while
    failing closed on the weakest.
  - v1 cited the walkthrough engine's `BINARY_SHA256` preflight as
    precedent for refuse-by-default. That preflight **warns and then
    verifies instructions at claimed addresses** — the opposite of what
    v1 proposed. The precedent argues against v1.
- **v2 — REJECTED.** Two of six blockers fixed (two-authorities,
  round-trip); the merge layer was still wrong, and for one root cause:
  `facts` was an object with **one value per key**, yet the rules said
  "different scope → both retained." The structure could not represent
  what the rules required. Consequently the prose was self-contradictory
  and `--resolve=<key>:<provenance>` could not even name one of two
  conflicting `measured` candidates. Also: demoting provenance to express
  applicability "rewrites what happened"; the verification gate was
  undefined for the majority of facts that are not address claims;
  `derived_from` used `@` as a separator when fact keys already contain
  `@`; libc had no identity of its own; `process`/`attempt` scopes had no
  IDs to be checked against.
- **v3 — REJECTED.** The candidate-set structure was accepted. The
  semantics written on top of it were not. Five defects, all of the same
  kind — English that reads as a rule but does not define a function:
  1. **Overlapping merge predicates.** Row 1 ("no candidate with same
     `applies_to` *and* same value → append") and row 3 ("candidate with
     same `applies_to`, different value, higher rank → supersede") both
     fire when the store holds *both* a same-value and a different-value
     candidate for one `applies_to`. The table was a list of hints, not a
     case analysis; its outcome depended on which row a reader checked
     first.
  2. **Dedup ignored provenance.** "Same `applies_to` and same value →
     update `last_seen`, no new candidate" silently collapses a
     `measured` 72 and an `asserted` 72 into one candidate, destroying the
     record of which authority said what — the exact loss v2 was rejected
     for.
  3. **No normative state transition.** `unresolved` appeared in the
     candidate `state` enum, but merge assigned it to *the key*
     ("the key is `unresolved`"), and nothing defined how anything leaves
     that state. Two different state spaces wearing one name.
  4. **Scope ordering undefined.** "narrower scope beats broader"
     presumes a total order over `build|libc_file|host|boot|process|
     attempt` that the document never gave.
  5. **`last_seen` breaks dependency digests.** `derived_from` pinned
     "sha256 of the candidate's canonical form" while merge *mutated
     `last_seen` on that same candidate*. Every re-observation of an
     unchanged fact changed its digest and therefore marked every
     dependent stale. The staleness mechanism would fire constantly and
     be turned off within a day.

## Goal

One document that every supwngo command can **write** and **read**, so a
fact learned by one command is reusable by another, and so a human can
supply facts supwngo cannot measure.

```bash
supwngo analyze binary_01 --context-out ctx.json
supwngo --context ctx.json pwn binary_01
```

## Non-goals

- Not a replacement for `core/database.py` (per-machine SQLite cache).
- **Not a serialization of `ExploitContext`.** Explicitly abandoned; see
  "One-directional flow".
- Not a wire protocol.

## Method: the normative artifact is code, not prose

v1, v2 and v3 each specified merge and resolution in English and each was
rejected for a defect that was *invisible in English and trivial in code*:
non-disjoint cases, a missing total order, a mutable field inside a digest.
Prose has no totality checker. A fourth prose round is predicted to fail
the same way.

So v4 inverts the artifact relationship:

- **`supwngo/schema/resolve.py` is normative.** The merge decision, the
  provenance order, the scope order, the specificity order, the candidate
  state machine and the digest projection live there as data and pure
  functions.
- **The tables in this document are generated from it.** A committed
  `docs/reference/context-resolution-tables.md` is produced by
  `python -m supwngo.schema.resolve --emit-tables`, and a test asserts the
  committed file is **byte-identical** to freshly generated output. Prose
  cannot drift from code, because prose is no longer hand-written.
- **Totality and determinism are executable properties**, not claims.
  Exhaustive enumeration over the bounded semantic domain, plus a
  **mutation meta-test** that each property actually fails against a
  deliberately broken resolver.

### Methods weighed

**Method A — reference implementation + generated tables + property tests
(CHOSEN).**
The semantics are Python; the tables are output; the guarantees are tests.
- *For:* a non-disjoint case analysis is a failing totality test, not a
  reading comprehension exercise. A missing total order is a failing
  antisymmetry/transitivity test. A mutable field inside the digest is a
  failing digest-stability test. All three v3-class defects become
  mechanically detectable. Reviewers read ~400 lines of pure functions
  with no I/O instead of 300 lines of English.
- *Against:* the reviewable artifact is code, so a reviewer who only reads
  the plan reviews a summary. Mitigated by inlining the resolver into the
  review prompt alongside the plan, and by the generated tables being the
  human-readable face of it.

**Method B — declarative rule table in JSON, resolver is a generic
interpreter (NOT TAKEN).**
Push all semantics into a data file; ship a small interpreter.
- *For:* the normative artifact is literally the table — no generation
  step, therefore no drift at all, and it is language-agnostic if supwngo
  ever grows a non-Python consumer.
- *Against:* the rules are not per-cell lookups. Maximal-element
  computation over a **partial** order, staleness closure over a DAG, and
  the digest projection cannot be expressed as table rows without an
  embedded expression mini-language — which relocates the ambiguity into
  an untested interpreter, a strictly worse place than Python with tests.
- *What would flip it:* if resolution were ever reduced to pure per-cell
  lookups with no graph traversal and no partial order, B becomes
  strictly better and A's generation step becomes pure overhead.

**Method C — formal model (TLA+ / Alloy) as the spec (NOT TAKEN).**
- *For:* exhaustive guarantees over small scopes, including properties
  exhaustive Python enumeration cannot reach.
- *Against:* the model is not the shipped code, so it adds a second
  authority that can diverge — the same two-authorities defect v2 was
  rejected for, one level up. Nobody in-tree can run it in CI.
- *What would flip it:* a second implementation (a Rust or Go consumer of
  the same documents) needing an arbiter that is neither implementation.

## Correction to this plan's own text (v3 was factually wrong)

v3 described the `DetailedProtections.to_dict()` bug as "adds ~20 fields …
emits 6". **The fix has landed at `ef40e93` and the numbers were wrong.**
Introspection at `ef40e93`:

| quantity | value |
|---|---|
| `Protections` declared fields | 8 |
| `Protections.to_dict()` emits | 6 |
| `DetailedProtections` declared fields | **22** |
| fields `DetailedProtections` adds over `Protections` | **14** |
| fields missing from the old serializer | **16** |
| `DetailedProtections.to_dict()` now emits | **16** |
| declared but deliberately **not** emitted (`_UNMEASURED`) | **6** |

The 6 in `_UNMEASURED` are `stack_clash_protection`, `safe_stack`, `cfi`,
`shadow_stack`, `rpath`, `runpath`. **`analyze()` never populates them.**
The fix declares them and deliberately does not emit them, because an
introspective serializer cannot distinguish *measured false* from *never
measured*, and would publish `cfi: false` that nothing computed —
indistinguishable from a measured `nx: false`.

**This is load-bearing for the provenance model, and v4 adopts it as an
invariant:**

> **Absent must not be representable as false.** A fact that was never
> measured has **no candidate**. `resolve()` raises `FactUnavailable`. No
> code path returns a type default for a missing fact, and no adapter may
> emit a fact key from a dataclass default.

Enforced three ways:
1. The protections adapter enumerates an explicit key list; it never
   iterates `dataclasses.fields()`. A test asserts the adapter's key set
   equals `fields(DetailedProtections) - _UNMEASURED`, so adding a
   measured field without adapting it fails, and adding an unmeasured
   field without declaring it fails. (This is the existing
   `tests/test_protections_to_dict.py` contract, extended to the adapter.)
2. `resolve()` has **no default parameter**. There is no
   `resolve(key, default=…)` overload to reach for. Callers that can
   proceed without a fact call `try_resolve()`, which returns an explicit
   `Absent` sentinel object that is not falsey-equivalent to `False` or
   `0` and raises `TypeError` on `bool()`.
3. A property test (P12) asserts that for every key in the registry, an
   empty candidate list yields `FactUnavailable` and never a value.

### `Confidence` has four members, and `asserted` is not one of them

Verified by introspection: `[m.value for m in Confidence]` is
`['measured', 'derived', 'assumed', 'unknown']`. v1–v3 all claimed the
provenance vocabulary was "carried over from `model.Confidence`". It is
not — `asserted` is a **fifth member this schema adds**, because the
walkthrough engine has no concept of a human supplying a value.

So the two models are not freely interconvertible and the plan must say
how they map, rather than implying they are the same enum:

| context `provenance` | walkthrough `Confidence` | note |
|---|---|---|
| `measured` | `MEASURED` | 1:1 |
| `derived` | `DERIVED` | 1:1 |
| `assumed` | `ASSUMED` | 1:1 |
| `unknown` | `UNKNOWN` | 1:1; both require a resolving step |
| `asserted` | *(none)* | **lossy downward.** A walkthrough generated from a document containing a selected `asserted` fact renders it as `ASSUMED` **and** must emit the operator attribution in the step text, so the reader is told a human supplied the number and is not led to believe the tool measured it. |

Widening `Confidence` with an `ASSERTED` member is the alternative and is
**not** taken here: it would change a merged, tested public enum in
`exploit/` for a consumer that does not exist yet. *What would flip it:*
the walkthrough engine growing its own operator-input path, at which point
one enum serves both and the mapping table should be deleted.

Phase 1 (`supwngo/schema/resolve.py` + its tests) imports nothing from
supwngo and is pure, so it is reviewable and testable on its own regardless
of either prerequisite.

## Design

### One-directional flow (unchanged from v3; accepted)

```
command results ──adapters──▶  facts  ◀──hand-authoring── human
                               │  ▲
                   evidence    │  │ projection (read-only)
                      ▼        │  ▼
                   blocks      └─▶ ExploitContext (in-memory, never written back)
```

- **`facts` is the only normative store.** A consumer reads `facts` and
  never a block.
- **`blocks` are non-normative evidence**, append-only, each carrying
  `produces: ["<fact_key>", …]`.
- **`ExploitContext` is a projection.** A loader populates only the fields
  it can. There is no `to_context_doc()`. It is never serialized back over
  facts.

Forced by the code, not preference:

- `core/context.py:16-28` forbids `core/` importing `supwngo.exploit.*`,
  and types two fields `Any` for exactly that reason
  (`verification_level` at `:256-261`, `attempts` at `:263-267`).
  A `from_context_doc()` must *construct* `AttemptRecord` and
  `VerificationLevel`, i.e. add the forbidden edge. Putting the model in
  `supwngo/schema/` — which may import from `exploit/` — removes the
  conflict.
- **Rehydration mutates what it rehydrates.** `LibcInfo.__post_init__`
  calls `_analyze_libc()` whenever `path` is set (`context.py:83-85`),
  recomputing `system_offset`/`binsh_offset`/hooks from the *local* libc —
  overwriting even a human's `asserted` values. `add_leak()`
  (`context.py:311-318`) re-triggers base derivation. `find_one_gadgets`
  **appends without clearing** (`context.py:130-133`), so each round trip
  lengthens `one_gadgets`. Round-tripping is not merely lossy, it is
  non-idempotent and monotonically corrupting.
- **Existing serializers are destructively lossy by design.**
  `AttemptRecord.to_dict()` reduces `payload: bytes` to
  `payload_len: int` (`contracts.py:104`) and `str()`s non-scalar
  `partial_artifacts` (`:106`). `Vulnerability.to_dict()` drops
  `controllable_input`, `primitives`, `crash`, `details`
  (`detector.py:91-101`). Adapters must read the **live objects**, not
  these `to_dict()`s.
- **Model ambiguity a schema cannot fix:** `ExploitContext.offset`
  (`:250`) and `stack.return_address_offset` (`:154`) are documented as
  deliberately distinct (`:244-249`). Resolve to one field with a stated
  meaning before mapping either to a fact key.

### Facts are candidate sets (unchanged from v3; accepted)

```json
"facts": {
  "stack.return_offset": {
    "candidates": [
      {
        "id": "f_c41d9a3b7e02",
        "value": 72,
        "provenance": "measured",
        "applies_to": {
          "identity": "t_main",
          "scope": "build",
          "conditions": {"input_method": "stdin"}
        },
        "derived_from": [],
        "method": "gdb_cyclic_probe",
        "by": "supwngo offset",
        "state": "active",
        "observations": [
          {"at": "<ISO-8601>",
           "evidence": {"rsp": 6748010543161397363, "cyclic_find": 72}}
        ]
      }
    ]
  },
  "resolutions": [ … ],
  "conflicts": [ … ]
}
```

Changes from v3, each fixing a numbered v3 defect or a round-1 finding:

- **`resolution` moves out of the fact** to a document-level
  `resolutions[]`. v3 stored `{"selected": …, "rule": …}` inside the fact,
  which made a *derived, context-dependent* answer look like stored state
  and is why defect 3 could exist. Selection is computed at read time from
  the invocation's context; the only persisted decision is an **operator
  pin**. (v3 defect 3.)
- **`state` ∈ `active | superseded | retracted`.** `unresolved` is removed:
  it was never a property of a candidate. Unresolvedness is an *outcome of
  `resolve()`*. (v3 defect 3.)
- **`id` is content-derived**, `"f_" + digest(ID_DIGEST_FIELDS)[:32]` (128 bits), not
  random. Round-1 finding 4 showed random ids make merge non-commutative
  (two dedup-equal candidates leave different survivors by insertion
  order) and finding 8 showed they make `min(id)` an arbitrary witness.
  Content-derived ids make both go away: dedup-equal ⇒ **same id**.
- **`evidence` moves into an append-only `observations[]`.** Round-1
  finding 3: a scalar observation counter discards the evidence of every
  observation after the first. Each observation carries its own `at` and
  `evidence`, so nothing is lost and re-observation still does not create
  a competing candidate. `last_observed_at` is *derived* (`max(o.at)`),
  not stored, which is also why it can no longer be order-dependent.
  (v3 defect 5, round-1 finding 4.)
- **`verification` is removed from the candidate entirely.** Round-1
  finding 3: a later `verified` observation could be permanently stuck
  representing itself as `unverifiable`, and upgrading it in place would
  change a digest-bearing field and mark every dependent stale.
  Verification is a function of *(candidate, loaded binary, available
  tooling)* — not a property of the candidate — so it is computed at read
  time and cached out of band in a non-digest-bearing
  `verification_cache` keyed by `(candidate_digest, verifier_version)`.
  The same candidate is honestly `unverifiable` on a machine with no
  disassembler and `verified` on one with it.

`provenance` ∈ `measured | derived | assumed | asserted | unknown`.
`unknown` is load-bearing: it requires the fact to name a `resolved_by`
step, mirroring `Confidence.UNKNOWN` (`walkthrough/model.py:130-149`).
`asserted` has no `Confidence` counterpart — see the mapping table under
"Prerequisites".

`scope` ∈ `build | libc_file | host | boot | process | attempt` — validity
domain, separate from provenance. `process`/`attempt`-scoped candidates are
**refused on reuse in a new run**, regardless of digest.

`depends_on` ∈ `binary_bytes | binary_symbols | libc_file | runtime`.

`conditions` makes jointly-valid facts explicit. A bare
`stack.return_offset: 72` is ambiguous because `offset --input-method
[stdin|argv|file]` (`cli.py:768`) yields different results per method and
`OffsetResult` (`offset_finder.py:28-42`) does not record which it used.

`confidence` is removed. v1 carried both `provenance` and `confidence` as
independent trust axes but merged only on provenance, so a `measured` fact
at 0.2 would supersede one at 0.99. Where a numeric score genuinely exists
(`Vulnerability.confidence`, `detector.py:75`) it lives in the evidence
block, not in resolution logic.

## The resolver (normative: `supwngo/schema/resolve.py`)

This section describes the reference implementation. **The generated
tables in `docs/reference/context-resolution-tables.md` are the normative
statement of every order and every case split**; what follows is the
design rationale a reviewer needs in order to judge the code.

The module is **pure**: stdlib only, no supwngo imports, no filesystem,
no clock, no randomness. Everything it needs is passed in. That is what
makes exhaustive property testing possible and what lets Phase 1 proceed
without the walkthrough branch.

### Store invariants (round-1 finding 2: totality needs preconditions)

Round 1 was right that "three disjoint cases" is not disjoint if one of them
is a validation guard that can also match a dedup key. So validation is
hoisted out of the case analysis and stated as **invariants every store
satisfies at all times**, checked transactionally on load and re-checked
after every mutation:

| # | invariant |
|---|---|
| I1 | `validate_candidate(c) == c` — **equality**, not "validation did not raise". Checking only that it did not raise ignored the normalised candidate it returns, so a hand-built candidate with duplicate or unsorted `observations` — which sit outside the id digest, where I2 cannot see them — validated clean and still changed the document bytes (round-3 finding 6). Validation covers `provenance`/`scope`/`state` ∈ enum, `id` matching `^f_[0-9a-f]{32}$`, well-formed `applies_to` and `derived_from` entries, non-empty `observations`, a non-negative int `generation`, and `DERIVED ⇒ derived_from` non-empty |
| I2 | `c.id == derive_id(c)` — the id is a function of the candidate's content. Enforced **inside** `validate_candidate`, and labelled there: the separate probe `validate_store` used to carry could never fire, because I1 rejects a mismatched id first (round-3 finding 4's defect class, found by this plan's own positive-control test rather than by a reviewer) |
| I2b | every candidate is filed under the key it claims |
| I3 | `dedup_key` is **unique among `ACTIVE` candidates of a key**; terminal candidates may share a dedup key with an active one |
| I4 | `c.value` satisfies the fact key's declared type **and** `c.applies_to.scope ∈ registry[key].allowed_scopes` |
| I5 | `derived_from` forms a DAG — no cycles; and every ref that resolves must name its source under the source's **own key** (`Ref.key == src.key`) |
| I6 | candidate ids are globally unique within the document |
| I7 | the append-only log is well formed **and referentially sound**: every record is a `PinRecord` of a known class under a **known fact key**, with a unique positive `seq`, non-empty `at`/`actor`/`reason`, candidate ids that **exist** and are filed under the record's own key, a replacement iff the class is `supersede`, no candidate named by an `unpin`, and a target whose state **matches** what the record claims happened. Shape alone let a record name a nonexistent candidate — and `resolve` then honoured the pin (round-3 finding 5) |
| I8 | no terminal state without a record: a `SUPERSEDED`/`RETRACTED` candidate must have the matching log entry, so a state change made outside the state machine cannot hide |
| I9 | `store.conflicts` is well formed, unique, canonically ordered, and names candidates that exist under the key each record claims. It is as public as `resolutions` and was validated nowhere, so a malformed entry survived a merge and surfaced later out of `canonical_document` (round-3 finding 6) |

`validate_candidate` rejects **any** malformed input with `SchemaError` and
is the only function permitted to raise on untrusted data, which is what
makes P1 hold over arbitrary dicts rather than only over well-typed ones
(round-1 finding 2, second paragraph).

**Totality is structural, not remembered** (round-2 finding 1). Field-by-field
checks alone let `observations=1` escape as a `TypeError` and let two evidence
values of incomparable types fail *inside* `sorted()`. So the public
`validate_candidate` is a funnel:

```python
def validate_candidate(raw):
    try:
        return _validate_candidate(raw)
    except SchemaError:
        raise
    except Exception as exc:            # deliberate funnel
        raise SchemaError(f"malformed candidate ({type(exc).__name__}: {exc})") from exc
```

P1b includes the one input that *only* the funnel catches, so the funnel is
demonstrably load-bearing rather than decorative — and the
`validation_not_funnelled` mutant is bound to P1b to keep it that way.
Constructed `AppliesTo`, `Observation` and `Ref` instances are **re-validated**
rather than trusted: a typed container is not a validated one.

**`generation`: why a re-observed retraction does not collide** (round-2
findings 2, 6, 11). `state` and `observations` are deliberately outside the id
digest, so retract-then-re-merge produced two candidates with one id — and a
single ambiguous id broke `by_id`, pins, dependency lookup, the conflict record
and array ordering simultaneously. The fix is a store-assigned
`generation: int` inside `ID_DIGEST_FIELDS` (but **not** in `dedup_key`, so
re-observation still dedups into an active sibling). Ids also widened from 48 to
**128 bits**: a 48-bit digest permits feasible birthday collisions, and every
ambiguity above becomes reachable without any hash collision at all.

**`generation` is store-assigned *unconditionally*** (round-3 finding 1). Rev 3
derived it from store state only when a terminal sibling existed, and took the
caller's value otherwise — so `generation` was an **input**, and merging the same
assertion at 0 and at 5 on a fresh store left whichever arrived first. Reversing
arrival order changed the canonical bytes, which is precisely what P2 exists to
forbid; P2 could not see it because its fixtures all carried the same
generation. Now:

```
generation = active sibling's generation      if one exists (this *is* that candidate)
           = 1 + max(terminal siblings')      if any have died
           = 0                                otherwise
```

Order-independence then rests on exactly two facts, together: `generation` is a
function of store state alone, and `dedup_key` excludes `generation` so the
lookups that compute it are themselves generation-independent. A **mapping** may
state `generation`/`id` as an integrity assertion and is refused if it disagrees;
a `Candidate` instance states *nothing*, because its fields are the store's own
earlier assignment — treating them as an assertion broke the round trip
`merge(store, validate_candidate(raw))`, since validation necessarily fills both
fields in and there was no way to express "I have no opinion".

### Merge is a precondition plus two disjoint cases, and never supersedes

```python
def merge(store: FactStore, incoming: Mapping) -> MergeDecision
```

**Three preconditions (none of them a case):**

1. `validate_candidate(incoming)` — raises `SchemaError`, store unchanged.
2. `candidate.state is transition(None, "append")`. The transition table is the
   **only** authority on states, so an incoming mapping claiming
   `state="retracted"` is a `SchemaError`, not an append. Round-2 finding 3 was
   that the state machine was tested but not *used*: `merge` appended whatever
   state arrived, which was also a second route to duplicate terminal/active
   ids. Patching the table now changes `merge`'s behaviour, which is what makes
   P11 load-bearing rather than decorative.
3. `validate_store(store)` — I1–I9 hold **before** the write. Round-2 finding 4
   was that `merge` *asserted* I3 instead of establishing it: a store that
   already violated I3 was left violating it unless the incoming candidate
   happened to collide. The old "duplicate active dedup key" guard inside the
   case analysis is deleted, because with this precondition it could never fire
   — and a check that cannot fail is worse than none.

The write itself is **transactional**: snapshot, mutate, `validate_store` again,
restore the snapshot and re-raise on any failure. Then, over a *valid* incoming
candidate and a store satisfying I1–I9, exactly two cases on a single
predicate:

| predicate | decision |
|---|---|
| ∃ the (unique, by I3) `c ∈ store[key]` with `c.state is ACTIVE` and `dedup_key(c) == dedup_key(incoming)` | `DEDUPED` — append `incoming.observations` into `c.observations`; **no** new candidate, **no** state change to anything |
| ¬∃ | `APPENDED` — added with `state=ACTIVE` |

`P` and `¬P` on one predicate: disjoint and exhaustive with nothing left to
forget. (v3 defect 1; round-1 finding 2.)

**Dedup considers only `ACTIVE` candidates** (round-1 finding 3). v4 rev 1
would have folded a fresh observation into a *retracted* candidate and
produced no active fact at all. Re-observing a retracted value appends a new
`ACTIVE` candidate at a fresh `generation` — it is genuinely new evidence — and
records a `reobserved_after_retraction` **or**
`reobserved_after_supersession` entry in `conflicts[]`, so the operator is told
rather than the retraction being silently undone. The two terminal states are
reported separately (round-2 finding 8): a retraction was a judgement that the
fact was *wrong*, a supersession that it was *stale*, and collapsing them told
the operator the wrong one had happened.

**The dedup key carries every digest-bearing field** (round-1 finding 3):

```python
def dedup_key(c):
    return (c.key, canonical(c.value), canonical(c.applies_to),
            c.provenance, c.method, c.by, canonical(c.derived_from))
```

- `provenance` is in it, so a `measured` 72 and an `asserted` 72 stay two
  candidates and the record of who said what survives. (v3 defect 2.)
- `method`, `by` and `derived_from` are in it, so two measured values from
  *different sources* or *different lineages* no longer collapse into
  whichever arrived first. (Round-1 finding 3.)
- `evidence` is deliberately **not** in it — evidence differs on every run
  (a raw `rsp` value), so including it would mean nothing ever dedups and
  the store would grow without bound. Evidence is preserved instead by
  `observations[]`, which is strictly better than being a dedup component.
- `verification` is not in it because it is no longer on the candidate.

Since `dedup_key` now equals `ID_DIGEST_FIELDS` up to `evidence`,
**dedup-equal implies id-equal** (I2), which is what makes the next claim
true.

### Merge is commutative, and the document digest is permutation-invariant

Round-1 finding 4 correctly demolished rev 1's commutativity claim on three
grounds. All three are closed structurally:

1. *"Dedup-equal candidates with different ids leave different survivors."*
   Ids are content-derived (I2), so dedup-equal candidates **are** the same
   id. There is no choice of survivor to make.
2. *"`last_observed_at` is order-dependent unless merge takes a maximum."*
   It is not stored. `observations[]` is held as a **canonically sorted
   set**, ordered by `(at, observation_digest)`, deduped by
   `observation_digest`; `last_observed_at` is derived as `max(o.at)`.
   Sorted-set union is commutative.
3. *"Two non-duplicate appends reverse the candidate-array order, and
   canonical JSON does not sort arrays."* Correct, and the fix is a
   normative serialization rule rather than a separate digest projection:

> **Canonical array ordering.** `canonical_document()` sorts every
> `candidates[]` by `id` (unique by I6, so no tiebreak is needed and none is
> hidden), every `observations[]` by `(at, observation_digest)`, every
> `resolutions[]` by **`seq`** (unique by I7), every `conflicts[]` by
> `(key, class, sorted ids)`, and every `derived_from[]` by
> `(key, id, digest)`. All sort keys are content-derived or store-assigned and
> **total**, so array order is a function of content, never of insertion order.

Round-2 finding 7 was that `derived_from` omitted `digest` from its sort key, so
two refs to the same `(key, id)` with different digests kept input order; and
round-2 finding 9 was that `resolutions[]` sorted on the operator-supplied `at`,
which is not a total order and not chronological. Both sort keys are fixed
above. `conflicts[]` is additionally maintained as a **set** (`_record_conflict`
inserts only if absent, then sorts), so recording the same conflict from two
merge orders cannot change the bytes either.

With that rule the document digest is permutation-invariant with no second
projection to keep in step — which is why rev 1's "no such projection is
specified" is answered by removing the need for one.

### Supersession and pinning have named owners (round-1 finding 7)

There is **no automatic supersession.** That is the point: `merge()` never
picks a winner. Exactly three actors can change a candidate's state, and
each leaves an audit record:

| actor | operation | effect |
|---|---|---|
| operator | `supwngo context supersede <id> --by <id> --reason <text>` | `ACTIVE → SUPERSEDED`, `resolutions[]` record |
| operator | `supwngo context retract <id> --reason <text>` | `ACTIVE → RETRACTED`, `resolutions[]` record |
| operator | `supwngo context pin <key>=<id>` / `unpin <key>` | `resolutions[]` record of class `pin` / `unpin`; the pinned candidate's rivals are **not** touched |

Every one of those four writers takes a mandatory **`actor`** and records it
(round-2 findings 5 and 10). A pin is the single mechanism by which an
`asserted` value may beat a contradictory `measured` one, so an unattributed
pin is not a record of an explicit operator decision — and before this fix
*any* caller could append a `PinRecord` to a public list and disable the guard
with no actor, no validation and no authorisation. There are now validated
`pin()` / `unpin()` writers, and I7 rejects a hand-appended record.

**Validate first, then mutate, then log** (round-2 finding 5).
`retract(store, id, at=None)` used to change the candidate's state and *then*
raise while building the record, leaving an unlogged mutation. Every lifecycle
write now validates its arguments and computes `transition()` **before**
touching the store, then commits transactionally with a snapshot. `supersede()`
additionally refuses the three ways the claim can be nonsense: self-supersession,
cross-key supersession, and supersession *by* a candidate that is itself
retracted or superseded.

**Current pin is a defined fold, not "if `ctx.pins` holds one".** Round-1
finding 7 is right that an append-only list is not a mapping — and round-2
finding 9 is right that the fold key was wrong:

```python
def current_pins(store):          # total, order-independent
    for key, records in group_by_key(records_of_class({"pin", "unpin"})):
        latest = max(records, key=lambda r: r.seq)     # store-assigned, unique
        yield key, latest.candidate_id if latest.cls == "pin" else None
```

`current_pins` **validates the log before folding it** (I7), because a pin is
read-time authority: the record granting an override is checked at the moment it
is honoured, not only when some later write happens to pass through `merge`. The
in-process trust boundary is not a wall — a caller holding the store object can
append to a list as easily as it can call `pin()` — but a forged record must be
well formed, uniquely sequenced and **attributed**, and it is in the audit log
either way. The enforceable boundary is the *document*, and I7 is what guards it.

`seq` is assigned by the store (`1 + max(seq)`), is unique by I7, and is the
**only** ordering key. `at` is operator text kept for human readers: folding on
it made `"t10"` lose to `"t9"` lexicographically, and equal or empty timestamps
fell back to whichever record had the larger truncated content hash — a rule
that was deterministic without being chronological. P16 now uses exactly that
`"t9"` → `"t10"` case as its fixture.

### Conflicts are computed on every write, not only on resolve

Round-1 finding 7's sharpest point: a producer-only workflow never calls
`resolve()`, so equal-maximal conflicts would accumulate in silence, and
*dominated* contradictions would never be reported at all. So `conflicts[]`
gets a normative computation rule and runs on **every write**:

```python
def conflicts(store, ctx) -> list[Conflict]                 # the resolve-time view
def context_free_conflicts(store, key=None) -> list[Conflict]   # what merge records
```

Two views, because round-2 finding 8 established that the single
context-scoped function could not do the job it was named for: **no write
called it**, and it *cannot* be called at write time, because a producer has no
`ResolveContext`. So `merge` calls `context_free_conflicts`, which classifies
every unordered pair of `ACTIVE` candidates for the touched key without an
applicability filter. That is deliberately over-inclusive — it may report a pair
some later context renders inapplicable — which is the safe direction.

For every such pair whose canonical values differ, emit exactly one record whose
`class` is the first of these that holds:

| class | condition | severity |
|---|---|---|
| `contradiction_measured_asserted` | one is `measured`, the other `asserted` | blocking without a pin |
| `equally_specific` | `compare_specificity` is `EQUAL` | blocking without a pin |
| `incomparable` | `compare_specificity` is `INCOMPARABLE` | blocking without a pin |
| `dominated` | one strictly dominates the other | informational |

`equally_specific` exists because `Ordering` has **four** members, so
"dominated" is *not* the complement of "incomparable": labelling an
equally-specific disagreement `dominated` told the operator that something had
won when nothing had. Both `resolve` and the conflict report go through **one**
classifier, `classify_pair`, because two copies of an ordered partition drift
and a drifted partition puts a conflict in two classes or none.

Same-value pairs are not conflicts; they are **agreement**, recorded as
`agreements[]` so that "two authorities concurred" is visible rather than
inferred — and decided by `agreeing()`, the *same* predicate `resolve` uses.
Testing equal values alone reported two different builds' `0x401234` as
concurrence, contradicting both `agreeing()` and P19 (round-2 finding 8).

Property P13 asserts every differing-value applicable active pair appears in
exactly one record, that each pair's **class** matches an independently computed
expectation (presence alone would pass a classifier that put everything in one
bucket), that every class is *reachable*, and that `merge` really did record the
write-time conflicts.

### Candidate state machine (generated by calling the real transition)

```
            append   supersede   retract
  (absent)  ACTIVE   REFUSED     REFUSED
  ACTIVE    REFUSED  SUPERSEDED  RETRACTED
  SUPERSEDED REFUSED REFUSED     REFUSED
  RETRACTED  REFUSED REFUSED     REFUSED
```

Terminal states are terminal — a resurrected candidate would invalidate
every `derived_from` digest taken while it was dead. `REFUSED` raises
`StateTransitionError`; it is never a silent no-op. P11 asserts the table is
**total** over `(state, event)`, so a new state or event that is not
classified fails the test rather than falling through. (v3 defect 3.)

`merge` now derives the state it appends from `transition(None, "append")`
rather than accepting whatever arrived, so this table governs writes instead of
merely being tested (round-2 finding 3).

### Provenance is a partial order, generated from 4 covering edges

"Ordinary `asserted` must not beat contradictory `measured`" is not
expressible as a rank, because a rank is a total order and a total order
always picks a winner. It is expressible as **incomparability**:

```python
PROVENANCE_EDGES = (            # (dominates, dominated)
    ("measured",  "derived"),
    ("derived",   "assumed"),
    ("asserted",  "assumed"),
    ("assumed",   "unknown"),
)
```

The 25-cell table is the transitive closure, computed at import:

- `measured ≻ derived ≻ assumed ≻ unknown`
- `asserted ≻ assumed ≻ unknown`
- **`measured ∥ asserted`** and **`derived ∥ asserted`** — incomparable.

Transitivity holds by construction. P4 asserts irreflexivity, antisymmetry,
transitivity and symmetry of incomparability, and pins
`compare("measured","asserted") is INCOMPARABLE` as a named regression.

**Cost, stated honestly:** `asserted` cannot override anything supwngo
measured without a pin. Intended — `asserted` exists for facts nothing else
produced, where there is no rival and resolution succeeds immediately.

### Scope is a partial order over a containment DAG, plus per-key allowed scopes

Round-1 finding 6 was right that a single total order is semantically
false: `libc_file` and `host` are independent axes, and under rev 1 a
host-scoped candidate beat a `libc_file`-scoped one for
`libc.system_offset` purely because `host` sat later in a tuple. Rev 2
replaces the tuple with a **containment DAG**, and specificity is its
reverse:

```python
SCOPE_EDGES = (                 # (contains, contained)
    ("build",     "host"),
    ("host",      "boot"),
    ("boot",      "process"),
    ("process",   "attempt"),
    ("libc_file", "process"),
)
```

Read as validity-domain containment: a fact valid for the build is valid on
every host, every boot, every process; a fact valid for a libc artifact is
valid in every process using it. Consequences, all generated:

- `build ≻ host ≻ boot ≻ process ≻ attempt` in specificity
- `libc_file ≻ process`
- **`libc_file ∥ host`, `libc_file ∥ boot`, `libc_file ∥ build`** — so the
  reviewer's `libc.system_offset` example is `INCOMPARABLE` and yields
  `FactUnresolved`, never "host wins".

**And the example cannot arise at all**, because the fact-key registry
declares `allowed_scopes` per key (I4):

| key | `allowed_scopes` | `depends_on` |
|---|---|---|
| `stack.return_offset` | `{build}` | `binary_bytes` |
| `gadget.*`, `plt.*`, `sym.*` | `{build}` | `binary_bytes` / `binary_symbols` |
| `libc.system_offset`, `libc.binsh_offset`, `libc.one_gadget.*` | `{libc_file}` | `libc_file` |
| `libc.base`, `leak.*`, `heap.base`, `stack.leak` | `{process}` | `runtime` |
| `env.*` | `{host, boot}` | `runtime` |
| `attempt.*` | `{attempt}` | `runtime` |

A `host`-scoped `libc.system_offset` is rejected by validation, not
out-ordered at read time. P5 asserts the scope relation is a strict partial
order and that every member of the `scope` enum appears in `SCOPE_EDGES`,
so adding a scope without placing it fails the build.

*Option not taken:* the total lifetime order of rev 1. Rejected because it
is semantically false on the `libc_file`/`host` pair, as round 1
demonstrated with a concrete key. *What would flip a return to a total
order:* nothing short of `libc_file` being shown to genuinely nest inside
the host chain.

### Specificity: provenance FIRST, then containment, then condition subsets

Round-1 finding 5 was the most serious finding of the round. Rev 1 put
provenance **fourth**, so a `measured` build-scoped 72 and an `asserted`
process-scoped 80 were decided by the *scope* component and 80 was selected
before incomparability was ever consulted. The ordering written to enforce
the operator's constraint violated it.

Rev 2 puts provenance **first**:

```python
def compare_specificity(a, b) -> Ordering   # GREATER|LESS|EQUAL|INCOMPARABLE
```

Lexicographic over four components, halting on the first that is not
`EQUAL`:

1. **provenance** — partial (above)
2. identity-bound (1) beats identity-agnostic (0) — total
3. scope containment — partial (above)
4. `conditions` — **subset containment**, partial

With provenance first, *every* applicable `measured`/`asserted` pair is
`INCOMPARABLE` in the first component regardless of scope, identity or
conditions. The operator's invariant is now a **structural consequence of
the component order** rather than a case the ordering happens to reach.

**Component 4 is subset containment, not a count.** Round-1 finding 9:
counting matched conditions is not logical specificity — two unrelated
one-condition predicates would compare equal, and two redundant conditions
would beat one stronger one. Instead `a ≻_cond b` iff `b.conditions` is a
**strict subset** of `a.conditions` and they agree wherever both constrain;
unrelated predicates are `INCOMPARABLE`. That is the subset lattice, a
genuine partial order, with the counting artifact gone.

**Time is deliberately not a component.** v3 ended with "then newest `at`",
which (a) is non-deterministic under equal or skewed timestamps — and with
*equal* timestamps a `>` tiebreak returns `GREATER` in both directions,
breaking antisymmetry outright — and (b) silently resolves exactly the
measured-vs-asserted conflict that must not resolve silently.

Because components 1, 3 and 4 are partial, the composition is a partial
order, so selection uses **maximal elements**, never "sort and take first":

```python
M = {c ∈ pool : ¬∃ c' ∈ pool with compare_specificity(c', c) is GREATER}
```

Maximality is order-independent, which is what lets P7 hold. A
lexicographic product of transitive component orders with
halt-on-incomparable is itself transitive and antisymmetric; P5 checks this
over the enumerated candidate universe rather than trusting the argument.

### A guard that does not depend on the ordering being right

Round-1 finding 5 also showed that resting the operator's invariant on a
component order is fragile — one reordering breaks it silently. So the
invariant is enforced **twice, independently**:

```python
def contradiction_guard(pool, pins) -> None
```

Before maximal elements are computed, scan every unordered pair in the
applicable pool; if one is `measured` and the other `asserted` and their
canonical values differ, raise `FactUnresolved` with class
`contradiction_measured_asserted` unless a current pin names one of them.
P9 is strengthened to quantify over **all** applicable contradictory pairs
across every scope, identity and condition combination — not just pairs
tied on the first three components, which is what rev 1's P9 wrongly
assumed.

### `resolve()` is total: one return type, five named refusals

```python
def resolve(store, key, ctx) -> Selected        # never a bare value
def try_resolve(store, key, ctx) -> Selected | Absent
```

1. `pool = [c for c in store[key] if c.state is ACTIVE]`
2. `pool = [c for c in pool if applicable(c, ctx)]` — pure predicate over
   identity match, scope liveness against `ctx.run_id/process_id/
   attempt_id`, and `conditions` compatibility. A candidate bound to
   another identity is **not demoted** — its provenance is never rewritten
   (the v2 finding); it is simply inapplicable here.
3. `contradiction_guard(pool, current_pins(store))`.
4. If a current pin exists for `key`: the pinned id must be in `pool`, else
   `PinInapplicable`. A pin is the **only** thing that selects against the
   specificity order.
5. `M = maximal(pool)`.
   - `M` empty → `FactUnavailable`
   - `agreeing(M)` → `Selected(value, witnesses=M, witness=min(M, key=id),
     rule="unique_maximal" if |M|==1 else "agreed_value")`
   - otherwise → `FactUnresolved(M)`
6. Any witness stale → `FactStale`.

**`agreeing(M)` requires more than equal encodings** (round-1 finding 8).
Rev 1 would have treated two `gadget.pop_rdi` candidates from *different
builds* that happen to share integer `0x401234` as agreement — a real
hazard under `--target-identity=none`. Rev 2:

```python
def agreeing(M):
    return (len({canonical(c.value) for c in M}) == 1
            and len({c.applies_to.identity for c in M}) == 1)
```

Agreement is only recognised **within one identity**. Cross-identity
candidates that coincide numerically are `FactUnresolved`, which is exactly
the right answer for the one flag that lets them meet.

`Selected` carries the **whole agreeing set** in `witnesses`, so a consumer
that needs lineage is not handed an arbitrary one; `witness` is a
designated representative, `min(M, key=id)`. That representative is *well
defined* rather than arbitrary (round-2 finding 11): past `agreeing()` every
winner carries the same value **and** the same identity, so any of them answers
the question identically, and with 128-bit content-derived ids the choice is
also stable across runs.

Every exit is one `Selected` or one of five declared exceptions —
`FactUnavailable`, `FactUnresolved`, `FactStale`, `PinInapplicable`,
`SchemaError` (plus `StateTransitionError` from the state machine, which
`resolve` cannot reach). None is ever swallowed into a default.

### Digest projections: three, each named, with a declared partition

Round-1 finding 8 flagged the circularity in content-derived ids; finding 3
the verification upgrade problem; v3 defect 5 the mutable-field-in-digest
bug. Three explicitly named projections settle all of them:

```python
CONTENT_FIELDS    = ("key", "value", "provenance", "applies_to",
                     "derived_from", "method", "by")   # = dedup_key
ID_DIGEST_FIELDS  = CONTENT_FIELDS + ("generation",)
DEP_DIGEST_FIELDS = ID_DIGEST_FIELDS + ("id",)
DERIVED_FIELDS    = ("observations", "state")      # never in any digest
```

- `dedup_key` is `CONTENT_FIELDS` and **excludes `generation`**, so a
  re-observation still dedups into its active sibling; `derive_id` **includes**
  it, so a re-assertion after a retraction gets a distinct id. That one-field
  difference between the two projections is what closes round-2 finding 2.
- `derive_id(c) = "f_" + sha256(canonical(project(c, ID_DIGEST_FIELDS)))[:32]`.
  `id` is excluded from its own input, so there is no circularity (I2 then
  checks the fixpoint). 32 hex digits = 128 bits, per round-2 finding 6.
- `candidate_digest(c) = sha256(canonical(project(c, DEP_DIGEST_FIELDS)))`
  is what `derived_from` pins. It includes `id`, so a dependent records
  *which* candidate it used.
- `observations` moves on re-observation and `state` moves on
  supersede/retract, so neither is in any digest. `state`'s exclusion is
  load-bearing: if superseding changed the digest, every dependent's
  recorded `derived_from[].digest` would stop matching, making a legitimate
  supersession indistinguishable from tampering. That exclusion is **only** safe
  because an id identifies exactly one immutable candidate, which is precisely
  what `generation` and the 128-bit width above are for — round-2 finding 11
  was right that the partition was locally correct while its safety assumption
  was violated elsewhere.

P10 is the executable form: **mutating any `DERIVED_FIELDS` member must not
change either digest; mutating any other real field must change both.** The
test iterates the actual field list, so a field in neither partition fails —
the anti-vacuity guard this project's standing rule demands.

### Staleness: one mechanism, computed, never persisted

Round-1 finding 10 correctly observed that rev 1 alternated between four
mechanisms — recursive computation, a persisted `stale` flag, event-driven
closure invalidation, and pin-driven invalidation — and chose none. Rev 2
chooses **one and deletes the other three**:

```python
def is_stale(store, c, _seen=None) -> bool      # pure, terminating
```

`c` is stale iff any entry of `c.derived_from` is missing from the store, names
its source under a **different key** than the source's own (round-2 finding 7 —
a structurally false reference must not read as fresh), has a
`candidate_digest` mismatch, is not `ACTIVE`, or is itself stale.
Recursion carries a visited set, so it terminates even on an input that
somehow contains a cycle; I5 rejects cycles at validation anyway.

In fact a cycle is **unconstructible** through the public writers, not merely
rejected: a ref pins its source's digest, and the source's id is a function of
its own content *including its refs*, so closing a cycle would require the
digest of a candidate that does not exist yet. P17 asserts that
(`derive_id(self_ref) != solo.id`) rather than asserting it in prose. The
diamond case — one source reached by two paths — is also enumerated, because a
shared visited set is exactly the kind of optimisation that can mask a genuine
staleness.

There is **no `stale` field**, no invalidation event, and no transactional
closure update to get wrong. Supersession and pinning invalidate dependents
*automatically*, because the source stops being `ACTIVE` and the recursive
predicate sees that on the next read. Four mechanisms collapse to nothing to
maintain.

`derived_from` entries are `{"key": …, "id": …, "digest": …}` — the `key`
added per round-1 finding 10, so a dependent can be located without scanning
every key, and structured rather than a string because fact keys already
contain `@` (the v2 finding).

Consuming a stale candidate is `FactStale`, a hard error — without it, a
corrected `puts` leak leaves `libc.base` silently wrong and every ret2libc
address built from it wrong.

### Verification is a registry, and may return "unverifiable"

**Scope note (round-2 finding 14).** `depends_on` and `verification_class` are
**declarations for the Phase-2 document layer**, not behaviour of the Phase-1
resolver. `supwngo/schema/resolve.py` is pure — it has no loaded binary and no
tooling — so it cannot verify anything and no longer contains comments implying
it does. The generated table says so in its own header. The one part of this
that *is* enforceable without a binary is enforced: `provenance is DERIVED`
requires a non-empty `derived_from`. Everything below is Phase 2, and the
conformance tests in that phase are where it becomes executable rather than
declared.

Every fact key declares a verification class; each class has a verifier
returning `verified | failed | unverifiable`:

| class | verifier | example keys |
|---|---|---|
| `instruction_at` | disassemble and compare mnemonics | `gadget.pop_rdi`, `plt.system` |
| `symbol_addr` | symbol table lookup | `sym.win` |
| `static_offset` | none available | `stack.return_offset` |
| `libc_offset` | resolve against the bound libc artifact | `libc.system_offset` |
| `runtime` | never verifiable statically | `libc.base`, `leak.puts` |

**Missing tooling yields `unverifiable`, never `verified`.**
`unverifiable` is not a pass — a safety-critical consumer refuses it
unless an explicit, per-key, recorded override exists. `failed` refuses
always. This is what makes the identity gate implementable, and it means
the gate degrades honestly on a machine without a disassembler rather
than pretending to have checked.

### Identity: verify, don't just hash

- Record `sha256` **and `build_id`** (`.note.gnu.build-id`), which
  survives `strip`.
- On read, a digest mismatch **warns**, then supwngo **verifies a sample
  of `binary_bytes` facts against the loaded binary**. Refuse on
  **verification failure**, which actually predicts wrongness, rather
  than on a hash difference. `walkthrough/common.py:384-387` already
  implements this check.
- The hash gate was both over- and under-restrictive: **over** —
  `exploit -r host:port` (`cli.py:242,264-266`) and `solve --remote`
  (`:2720`) load a local *copy*; stripping or a `.comment` change alters
  sha256 while every gadget and offset stays correct. **under** — a
  matching sha256 says nothing about the host's libc, yet
  `libc.base`/`system_offset`/one-gadgets are the facts most likely
  wrong and most catastrophic.
- `--target-identity=sha256|build-id|none` replaces v1's blanket
  `--context-mismatch=allow`. `none` permits *selection* of candidates
  bound to a different identity and records an `identity_override` in
  `resolutions[]`; it does **not** disable verification, and
  `runtime`-scoped candidates remain refused.
- `Binary.__post_init__` hashes only `if self.path.exists()`
  (`core/binary.py:137-142`), so a doc can carry `sha256: ""`. **Refuse
  to write** a doc with an empty digest.

### Identities are first-class, and there is more than one

```json
"identities": {
  "t_main":  {"role": "target", "sha256": "…", "build_id": "…",
              "format": "elf", "elf_type": "ET_DYN", "linkage": "dynamic",
              "pie": true, "os_abi": "linux", "arch": "amd64", "bits": 64},
  "l_glibc": {"role": "libc", "sha256": "…", "build_id": "…",
              "version": "2.39"},
  "r_prod":  {"role": "remote", "endpoint": "host:1337"}
},
"runs": [{"run_id": "r_01", "at": "…", "process_ids": ["p_01"]}]
```

- Every candidate's `applies_to.identity` names one of these, bound to
  **the identity actually observed**, never to a stale envelope value.
- **libc gets its own identity**, because `libc.system_offset`,
  one-gadgets and every derived base bind to the libc, not the target.
- `process`/`attempt` scopes reference `run_id`/`process_id`/
  `attempt_id`, which is what makes "refused on reuse in a new run"
  implementable. A new `run_id` per CLI invocation; a new `process_id`
  per spawned or reconnected target process.
- `diff` and `batch` become representable: multiple `target`-role
  identities, facts bound per identity.

`exec|dyn|static` (v1) conflated two dimensions — PIE is normally
`ET_DYN`. Split into `format`, `elf_type`, `linkage`, `pie`, `os_abi`,
`build_id`. `Binary` has **no `to_dict()`**, so `target` needs a new
producer.

### Secrets and flags

`ExploitContext.captured_flag` (`:254`) and `VerificationReceipt.flag`
(`contracts.py:133`) must **not** be serialized by default. The
walkthrough engine deliberately filters flag-shaped strings so its
artifact cannot be used to skip the exercise
(`walkthrough/facts.py:14-20,55-62`); writing flags here would reverse
that control. Reuse its `_is_flagish`; gate on `--context-include-flags`.

`method`/`evidence` carry structured fields, not verbatim command lines
(usernames, tokens, remote endpoints). `target.path` and
`artifacts[].path` are **relative to the document**, with `--binary`
overriding at read time. Provenance commands are never executed.

### Encodings (pinned, because "canonical" is meaningless otherwise)

- bytes → base64 with a `b64:` prefix (never `default=str`, which yields
  an irreversible repr; today's habit at `cli.py:126,1601,1761,1765,…`).
- sets → sorted arrays (`profile_bad_bytes`, `context.py:280`).
- addresses → unsigned int; the schema **rejects** hex strings. In-tree is
  currently inconsistent (`hex()` at `detector.py:96`,
  `offset_finder.py:58-59`, `contracts.py:105`; raw ints elsewhere).
- canonical form: RFC 8785-style — `sort_keys=True`,
  `separators=(",",":")`, `ensure_ascii=False`, integers only where
  integral — plus a separate pretty presentation form that is explicitly
  **not** the digest input.
- YAML: `safe_load` only, duplicate keys rejected, anchors/aliases
  rejected, size/depth limits. YAML 1.1 parses `0x401234` as an int,
  which is why address encoding must be pinned for read parity.

### Persistence

`--context-out` defaults to the `--context` path (in-place accumulate).

Locking `ctx.json` itself does not serialize writers, because the file is
then *replaced* — the lock is held on an inode that no longer backs the
path. The lock lives on a **stable sidecar**, `ctx.json.lock`, and is held
across the whole read → merge → validate → temp-write → `fsync` →
`os.replace()` → directory `fsync` sequence. That is what prevents lost
read-modify-write updates, which atomic replacement alone does not.

**History stays inside the document.** Candidates that are `superseded`
or `retracted` remain in the candidate list with that state; a
`--context-prune` subcommand compacts them on request, so growth is
bounded by an explicit operator action rather than by a silent cap.

Long-running commands (`fuzz -t 3600`, `cli.py:135`) checkpoint
periodically so a killed campaign still contributes.

### Command tiers

Three tiers, with a literal table of all **32** `@cli.command()`
registrations at `ef40e93` (v3 said 31; verified by
`len(cli.commands) == 32`). Concrete exemptions:

- *No target*: `version` (`:1401`), `cyclic` (`:888`), `cyclic-find`
  (`:899` — it produces an offset with no binary, which would manufacture
  the exact unanchored-fact footgun this plan exists to prevent),
  `libc-id` (`:567`).
- *Target is not the binary*: `onegadget <libc>` (`:826`),

- *Not one target*: `diff <b1> <b2>` (`:1698`), `batch <dir>` (`:924`).

- *Argument-shape traps*: `triage <crash_dir> <binary>` (`:198`) — the

  argument is the target" is wrong. The decorator therefore takes an
  explicit **target resolver per command**, never positional inference.

Roughly 25 of 32 commands never build an `ExploitContext` at all — a
further argument for the projection model.

#### The narrowness annotation

Round 3's sharpest lesson was not about any one defect: **seven of its nine HIGH
findings were invisible to the property suite rather than absent from it.** The
properties ran hundreds of cases each and held the one dimension that mattered
constant. That failure mode is worse than an empty assertion, because the case
counts and the pass counts both look healthy — **narrowness reads exactly like
correctness.**

So the suite now carries a closed `DIMENSIONS` vocabulary (**27** entries across
candidate content, store shape and resolve context) and a `NARROWNESS` table
declaring, per property, which dimensions its input set *varies* and which it
deliberately *holds constant*. Three meta-tests enforce what is mechanically
enforceable:

| Meta-test | Asserts |
| --- | --- |
| `test_every_property_declares_what_it_varies` | every property is annotated, every name is drawn from the closed vocabulary, nothing is claimed both varied and held |
| `test_no_dimension_is_unvaried_by_the_whole_suite` | **no dimension is varied by zero properties** — the P27 trick one level up. A schema field nothing exercises is a direction along which the suite cannot fail, however many cases it runs |
| `test_single_fixture_properties_are_declared_as_such` | a property whose `varies` is empty must be on an explicit list (only P3, idempotence, is), so *unintended* single-case properties surface |

What these cannot check is whether a declaration is **true** — that is a reading
task. The annotation's purpose is to make it a 29-claim audit instead of a
29-property excavation, and to make the next such audit mechanical.

The table also reports, without asserting on it, every dimension varied by
**exactly one** property — that property is the entire coverage of that
dimension. Currently three: `binding` (P9 only), `dedup_collision` (P1 only),
`dependency_depth` (P17 only).

All three meta-tests were shown to go red, as the project's standing rule
requires, against six deliberate mutilations of the annotation: a dropped
annotation, a dimension outside the vocabulary, a dimension claimed both ways, a
new vocabulary entry no property claims, a dimension losing its only claimant,
and a property silently becoming single-case. **The first attempt at the
fifth control came back GREEN** — it stripped `evidence` from P21 on the
assumption P21 was its only claimant, but P1b varies `evidence` too. The control
was wrong, not the gate; solo dimensions are now computed rather than guessed,
which is exactly the class of mistake the printed solo list exists to prevent.

## Test strategy

### Properties (Phase 1; the gate this plan rests on)

`hypothesis` is **not installed** and is deliberately not added. The
semantic domain is bounded, so the properties are checked by **exhaustive
enumeration**, which is stronger than sampling and fully reproducible.

Round-1 finding 12 was right that rev 1 claimed exhaustiveness without
stating a bound — "every batch and every permutation" is infinite, and
factorial even under modest bounds. The bounds are therefore **normative
constants in the test module**, and the test **prints the realised case
counts**, so the bound is observable rather than asserted:

| bound | value | rationale |
|---|---|---|
| `PROVENANCES` | all 5 | complete |
| `SCOPES` | all 6 | complete |

| `VALUES` | `72`, `80` | agree / disagree; two suffice for every pairwise property |

### The mutation meta-test — this is not optional

This project has five recorded instances of a validation step that could
not fail (including a probe driver that omitted the argument it was
validating, and a test asserting `min(a, b) == expected`). Round-1 finding 11
found the same disease in rev 1's own mutant list: four of eight mutants
would **not** have failed the property they were bound to. Each of the 29
mutants below is bound to a **semantic** property, and the meta-test asserts
*that named property* fails — not merely that something failed.

Round-2 finding 13 then found the **converse** gap: the claim "every property is
paired with a mutant" was true of the mutants and false of the properties — six
properties (P1b, P3, P5b, P6, P7, P17) had no mutant bound to them, so nobody
had seen them fail. Six mutants were added and a second meta-test,
`test_every_property_has_a_mutant`, now asserts the direction that was missing.
The meta-test also distinguishes a detected violation (`AssertionError` or a
failed `pytest.raises`) from a *crash* inside the patch (`TypeError`,
`NameError`): a crash **fails the meta-test**, because a mutant that merely
breaks the code proves nothing about the property.

**It worked on first run.** The meta-test reported five toothless bindings,
each a real defect in the test suite rather than in the resolver:

1. `dedup_ignores_provenance` passed P14 — the fixture's two operands also
   differed in `method`, so they would not have deduped anyway. The fixture
   now asserts they differ *only* in provenance.
2. `dedup_matches_terminal` passed P1 — no enumerated store held a terminal
   candidate, so the mutation was unreachable. P1 now enumerates
   `retract_first ∈ {False, True}`.
3. `unsorted_candidate_array` passed P2 — array order is defended on both the
   write side (`FactStore._sorted`) and the read side
   (`canonical_document`), and removing only one was masked by the other.
   The mutant now removes both.
4. + 5. `provenance_fourth_and_guard_disabled` and
   `resolve_returns_default_on_empty` were *caught* but reported as escapes,
   because a failed `pytest.raises()` raises `_pytest.outcomes.Failed`, which
   derives from `BaseException`, not `Exception` — so the meta-test's own
   `except` clause was too narrow. That is a validation step that could not
   fail, found by the mechanism built to find them.

|---|---|---|---|
| `merge_supersedes_on_rank` | v3 defect 1 | **P1** | changes a pre-existing candidate's `state`, which `expected_active` forbids |
| `dedup_ignores_provenance` | v3 defect 2 | **P14** | the two authorities collapse to one |

### Why the byte gate is not theatre (round-1 finding 13)

Round 1 was right that a generator backed by parallel constants can agree
byte-for-byte with itself while disagreeing with resolution. So the
generator is forbidden constants: the provenance matrix calls
`compare_provenance(a, b)` for all 25 pairs, the scope matrix calls
`compare_scope`, the state table calls the real `transition()`, and the merge
table calls the real `merge()` against synthesised stores. P15 re-derives
**every cell of every table** independently in the test — and asserts no matrix
row was left unparsed — so a future refactor that introduces a parallel table
fails. Parsing only the provenance matrix, as rev 2 did, left the other four
tables ungated (round-2 finding 12). The byte gate then adds what it is
actually good for — catching an edit to the committed table that no code
change justifies — and nothing more is claimed for it.

### Document-level tests (Phase 2)

The v1 "byte-identical round trip" assertion is unachievable and is
replaced by three that are:

1. **Fixpoint stability:** `dump(load(dump(load(d)))) == dump(load(d))`.
   Catches non-idempotent rehydration.
2. **Semantic equality modulo a declared volatile set** (`updated`,
   `last_observed_at`, `runs[].at`, `receipt.verified_at`), the exclusion
   list living in the test so it shows up in diffs. `at` is an
   *observation* time and is never refreshed, so it is not volatile.
3. **No-silent-drop:** against a golden maximally-populated document,
   every JSON pointer in the input is present in the output. The
   `KNOWN_LOSSY` allowlist is restricted to fields explicitly deprecated
   with a migration rule; **unknown fields must round-trip unchanged**.

Plus: dependency-graph cycle and dangling-reference rejection at
validation; verifier registry per class (missing tooling →
`unverifiable`, refused by a safety-critical consumer; `failed` always
refuses); identity behaviour (mismatch warns, verification failure
refuses, `process`-scoped refused in a new run, `--target-identity=none`
records the override and still refuses `runtime`); secret redaction;
YAML/JSON parity including `0x401234` vs `4198964`; atomicity under
interrupt and concurrent writers; and packaging (schema loads via
`importlib.resources` from an installed wheel).

### Conformance tests (Phase 3)

- **Static conformance** over `cli.commands`: every one of the 32
  commands is either in the exemption allowlist **or** accepts both
  flags. v1's test was vacuous — a new command omitting the decorator

## Risks

- **`merge` is O(n) in the store and therefore O(n²) to build a document.**
  Validating I1–I9 before *and* after every write is what closes round-2
  finding 4, and it is the right default for a reference implementation whose
  job is to be obviously correct. It is **not** the right cost for bulk
  loading, so Phase 2 owes a `load()` that appends a validated batch and
  checks the invariants **once** at the end, with the same
  snapshot/rollback boundary. Named here rather than discovered later: the
  fix is a second entry point, not a weakening of `merge`.
- **The in-process store is not a security boundary, and `seq`/`actor` are
  forgeable.** A caller holding a `FactStore` can append to `resolutions[]` as
  easily as it can call `pin()`. Round-3 finding 5 is right that I7 does not
  make the log unforgeable, and **no in-process test could show that it did** —
  the attacker and the defender are the same process, so "unforgeable" is not a
  testable claim here. What *is* enforced, and tested by P22, is that every
  record crossing the document boundary must be well formed, uniquely sequenced,
  **attributed**, referentially sound and consistent with the candidate it names
  — checked on write *and* at every read that honours it. The enforceable
  boundary is the document, which is now validated on both sides by `merge`,
  `resolve` and `canonical_document` alike. A capability model inside one
  process would be theatre; stating the limit is not.
- **The resolver is now the spec, so resolver review quality is the
  project's risk.** Mitigated by the mutation meta-test (a reviewer can
  check that each historical defect is represented) and by the generated
  tables being diffable.
- **Generated-table byte gate can rot.** If the generator's formatting
  changes, an unrelated commit fails the gate. Accepted: a noisy gate is
  better than silent prose drift, and the fix is one regeneration
  command. The gate compares bytes, not a parse, on purpose — parser-based
  gates in this org have been downgraded to byte snapshots for exactly
  this reason.
- **`asserted` is weaker than operators may expect.** Contradicting a
  measurement now requires `--pin`. Documented in the CLI help text and
  in the error message of `FactUnresolved`, which names the pin command
  to run.
- **Walkthrough branch unmerged.** Phase 1 is independent of it by
  construction; Phases 2–3 are not, and the provenance vocabulary must be
  re-derived from `model.Confidence` as merged.
- **`cli.py` is ~2,900 lines with concurrent editors.** Phase 3 starts
  after the walkthrough CLI commit lands.
- **Real unit of work is depth, not breadth** — v1 claimed otherwise.
  `AttemptRecord`, `Vulnerability` and `DetailedProtections` each need a
  *new* non-lossy serializer. Sequence: resolver, then envelope + `facts`
  + 3 blocks on the core path, then widen.
- **Breaking consumers** of today's ad-hoc JSON: `--legacy-json` on the
  commands CLAUDE.md documents (`analyze`, `fuzz`, `triage`, `exploit`,
  `rop`, `symbolic`, `libc-id`), byte-identical to today, with a stated
  deprecation horizon.
- **Forward compatibility:** refuse unknown major `schema_version`;
  warn-and-proceed on a newer `tool_version`; preserve unknown fields
  without consuming them.
- **Diagnostics must go to stderr.** 19 commands print JSON to stdout via
  `console.print_json` (`cli.py:88,733,792,850,1116,…`); a warning through
  the same `console` makes stdout unparseable. Conflicts additionally
  appear as a machine-readable `conflicts[]` inside the payload.

## Review record — round 4 on v4: the stop condition, and why

Round 4's brief made the author's own best finding its centrepiece —
**narrowness in a property test reads exactly like correctness** — and asked one
primary question: for each of the 29 properties, which dimension does it claim to
constrain, and does its input set actually vary that dimension? It also required
every finding to be reported **by class with the sweep run**, not as an instance,
because the measured cause of a fourth round in this repo is that reviews report
instances, revisions fix instances, and the class survives.

**Verdict: NOT-APPROVED, 13 HIGH — RECURRENCES 6 / NEW 0 / INTRODUCED 7.**

`docs/plans/2026-09-24-context-schema-v4-review-round4.md`. Held, not

### The finding that matters most

Of the eight properties round 3's remediation added, **five are narrow or dead in
precisely the way round 3's own lesson describes**, and for **all eight**
round-3 mutant bindings a subtler mutation of the same rule survives:

| binding | the subtler edit that survives |
| --- | --- |
| `generation_from_caller` → P20 | enforce the mismatch only when `generation > 0`; or use `terminal[0].generation + 1` instead of `1 + max(...)` — P20 never has two terminal siblings |
| `canonical_coerces_keys` → P21 | keep keys and the bytes tag correct but encode enums as raw values, tuples as arrays, sets as sorted arrays, dataclasses as mappings — **the pristine canonicaliser already collides this way** |
| `log_shape_only` → P22 | delete only duplicate-`seq` rejection; every negative P22 fixture holds one record |
| `conflicts_unvalidated` → P23 | delete only the canonical-order comparison; the "out-of-order" control appends a *duplicate*, which trips an earlier clause |
| `supersede_key_only` → P24 | compare identity, scope and conditions but omit `binding`, which P24 never varies |

| `store_invariants_disabled` → P27 | keep I9 but delete only conflict-list ordering; P27's I9 control is a non-`Conflict`, so it never reaches the later clauses |

The pattern is one thing said eight ways: **a mutant that disables a rule proves
only that the rule is present.** Every one of these properties was demonstrated
`[RED]` in round 3, and that demonstration was true and insufficient — the
project's standing rule, *prove the gate goes red*, is necessary but does not
establish that the gate goes red for the right reason. That is the round's most
transferable lesson and it generalises past this artifact.

### The annotation table passes a well-formed lie

The narrowness annotation added before round 4 was intended to turn a
29-property excavation into a 29-claim falsification, and it did — the reviewer
used it and **named seven claims in it that are false**: P2 claims
`log_record_count` varies when the seeded store always contributes exactly one
record; P3 claims `observation_at` constant when it explicitly moves `t1` to
`t2`; P6 and P25 claim context-binding variation when every candidate is
BUILD-scoped; P8 claims identity and conditions constant when both vary; P10
claims scope and conditions vary when only identity inside `applies_to` changes;
P16 claims candidate `observation_at` varies when it is the *log's* `at`; P5b's
claimed id perturbation is not one, because `dataclasses.replace` retains the id.

So the three annotation meta-tests — proven red against six mutilations of the
table — are still a gate that a *true-shaped but false* claim passes. This is the
project's ninth-plus instance of the same shape in a new dress: the gate checks
the **form** of the claim, not its truth. The reviewer's fix is specific and
implementable: record **relational** projections at instrumented call sites, not
raw fields, because `process_id` changing is not binding variation unless
`candidate.applies_to.binding == context.binding_for(scope)` changes with it.

### The trust boundary was too broad, as suspected

The challenge to the `seq`/`actor` scoping was upheld. Authenticity genuinely
needs an external anchor — a key the mutating process does not hold, an
externally committed hash-chain head, or append-only storage outside the caller's
capability; an unkeyed chain in the same document is recomputable by the forger.
But **seven internal-consistency properties are expressible in-process and are
not asserted**: `seq` positive/unique/dense, at most one terminal event per
candidate, supersede endpoints describing the same proposition, a replacement not
already terminal at its own `seq`, lower generations terminal before higher ones
appear, terminal `seq` increasing along a generation chain, and I8's converse.
Writer reachability is itself expressible: generate histories only through the
public writers, then mutilate one relational fact and require refusal. Three
further candidates (actor consistency, `at` monotonicity, list order vs `seq`) are
policy-dependent and correctly excluded. The untestable third was being used to
wave through the testable two thirds.

### Refusal coverage is mechanical, and 29 refusals have never fired

Independently of the review, an author-side mechanical sweep — patch each error
class's `__init__` to record the raising site, run the whole suite, diff against
every `raise` in the module's AST — reports:

```

bare re-raise sites (exempt):                   4
NEVER FIRED by any test in the repo:           29
positive-control coverage of refusals:      78/107
```

This refines the answer to "can P27 generalise mechanically?": for *dimension

Recorded rather than landed: adding a gate to an artifact a reviewer has just
recommended splitting is the wrong direction.

### What round 3 changed about the property set itself

The coordinator's instruction for this pass was that each HIGH must name the
property test that would have caught it. Doing that exposed a structural gap
worth recording: **six of the nine HIGHs were invisible to the property set
because the properties quantified over fixtures that held the defective
dimension constant.** P2 could not see order-dependent `generation` because
every fixture shared a generation; P6 could not see context validation because
there was one context; P5 could not see scope-specific composition because the
universe held three of six scopes. The properties were not wrong — they were
*narrow*, and narrowness in a property test reads exactly like correctness.

That is why rev 4 adds breadth (7 contexts, all 6 scopes, generation variants)
rather than only adding new properties, and why P27 exists: it is the first
check here that asserts the **coverage relation itself** rather than a
behaviour, and it would fail if a future invariant were added without a way to
make it fail.

One finding was **not** expressible as a property test, and is recorded as such
rather than papered over: finding 5's observation that `seq` and `actor` are
forgeable by any caller holding the store. No in-process test can establish
unforgeability, because the attacker and the defender are the same process.
What is testable — that a forged record must be well formed, sequenced,
attributed and consistent, and is refused at every read — is what P22 asserts;
the rest is a **trust-boundary statement**, now written into both the Risks
section and `_validate_log`'s docstring instead of being implied by the word
"append-only".
