# supwngo Fix & Improvement Opportunity Catalog

> Companion to `docs/plans/2026-09-23-effectiveness-and-usability.md`. That plan is the *actionable, phased* answer to the user's two goals; this document is the *exhaustive* answer to "fan out and find all opportunities for fixing and improvement" — every concrete, evidenced issue found across the codebase, whether or not it's on the plan's critical path. Produced by 8 parallel subsystem audits + an independent codex peer review + direct verification of the highest-stakes claims. All findings are file:line-grounded; nothing here is speculative.

---

## 0. BLOCKING — the package does not import (found by peer review, verified directly)

**This supersedes everything else in severity: as of this snapshot, `import supwngo` fails immediately on Python 3.11** (the interpreter installed in this environment, and within the `>=3.8` range `pyproject.toml`/`setup.py` both declare). `supwngo/__init__.py` → `exploit/strategy.py` → `exploit/__init__.py` → `exploit/seccomp.py:361` raises `SyntaxError: f-string expression part cannot include a backslash` (an f-string containing `\x00`/`\n` — only legal under Python 3.12's PEP 701 relaxed f-string grammar). **All 31 CLI commands are unreachable** until this is fixed, because `cli.py` imports from the `supwngo` package.

Full-repo AST sweep (158 files) found exactly 4 files that fail to parse on Python 3.11:
- `supwngo/exploit/seccomp.py:361` — backslash inside f-string (PEP 701, needs 3.12+, or refactor to assign the escaped string to a variable first).
- `supwngo/exploit/auto.py:2746` — unterminated triple-quoted string literal (this one's a genuine bug, not a version issue).
- `supwngo/exploit/templates.py:269` — f-string brace mismatch (`{"" if ... else '''` — nested quoting error, genuine bug).
- `supwngo/distributed/coverage_merge.py:718` — `sum(1 for edge in ... if X if Y else Z)` — two `if` clauses in a generator expression is invalid syntax outright, on any Python version (genuine bug, not version-related).

**Impact on the rest of this catalog:** every other finding below was produced by *static reading* — none of the 8 parallel audits actually tried to `import`/run the code, so they all implicitly assumed the package loads. It doesn't, right now, out of the box. **Fixing these 4 files is a ~1-hour mechanical fix and must be the literal first commit of any work here** — it's Phase 0 in the updated plan.

## 1. Core substrate (`core/`, `analysis/`, `utils/`)

- **CRITICAL — `utils/helpers.py:65-98` `cyclic()` is a broken de Bruijn generator.** Appends up to 4 chars/iteration from independent index math; windows are not unique (e.g. `"aaaa"` recurs at offsets 0,1,2 in its own output). `cyclic_find()` therefore returns wrong offsets. `analysis/dynamic.py`'s `find_buffer_overflow_offset` depends on this → wrong RIP offset → wrong payloads, silently. Also packs only `<I` (32-bit) in `cyclic_find`, so 64-bit RIP subsequences won't be located at all. **Note:** a separate, *correct* implementation exists in `exploit/offset_finder.py`'s `PatternGenerator`, which properly delegates to pwntools' real `cyclic`/`cyclic_find`. Two implementations, and the broken one is what `dynamic.py` actually calls — the same "duplicate implementations, wrong one wired in" pattern found at the engine level (Section 4) recurring at the utility level.
- **CRITICAL — `core/binary.py:319` FORTIFY false positive.** `fortify = "_chk" in str(self.symbols.keys())` substring-matches the dict's `repr()`; `__stack_chk_fail` contains `_chk`, so **every canary-enabled binary reports FORTIFY enabled** regardless of actual `_FORTIFY_SOURCE` status.
- **CRITICAL — `core/binary.py:324-334` RELRO misdetection.** pwntools `ELF.relro` returns `None/'Partial'/'Full'`; the wrapper's truthy-string handling causes Full-RELRO binaries with a writable-in-header `.got.plt` section to be reported as Partial. The *correct* detector (GNU_RELRO segment + `DT_BIND_NOW`) exists in `analysis/protections.py:_get_relro_type` — but `Binary.protections` (what `checksec()`/the rest of the pipeline consumes) uses the wrong one.
- **HIGH — `analysis/static.py:21/27 & 22/31` duplicate dict keys.** `sprintf`/`vsprintf` are each defined twice in `DANGEROUS_FUNCTIONS`; the later "format string" entry silently overrides the earlier "buffer overflow" entry, losing overflow classification for those functions.
- **HIGH — `analysis/static.py:249-255` dead caller-resolution.** First xref-loop body is a literal `pass`; the angr fallback's address comparison almost never matches. `find_dangerous_functions` falls back to `caller="unknown", caller_address=0` for every sink — loss of call-site precision that downstream exploit-strategy logic likely needs.
- **HIGH — untrusted-binary execution risk.** `analysis/dynamic.py` runs the analyzed target directly (multiple call sites) and `protections.py`/`context.py` invoke `ldd`/`one_gadget` on it, unsandboxed. For a tool whose entire purpose is ingesting adversary-controlled binaries, this is a real dogfooding gap (a malicious binary can execute arbitrary code the moment it's "analyzed," before any exploit is even attempted).
- **MEDIUM — silent partial-load on pyelftools failure.** `binary.py:296-299` only warns if pyelftools parsing fails; `segments`/`sections` stay empty, so `protections.py:_check_static` always returns `True` and RELRO detection silently reports "No RELRO" with no error surfaced.
- **MEDIUM** — `dynamic.py` leaks open file descriptors (`stdin=open(...)` never closed, multiple call sites); exploitability heuristic keys on `0x41414141` but inputs actually use `cyclic()` output, so it effectively never fires; `protections.py:_detect_libc_version` regex returns the soname digit (`"6"`) as if it were the glibc version; `protections.py.analyze()` re-runs full `strings()`+`ldd` on every call site with no caching; `core/database.py` has no `PRAGMA foreign_keys=ON` and `INSERT OR REPLACE` resets `created_at` on update.
- **MEDIUM — API/doc drift.** The repo's own `CLAUDE.md` advertises `binary.dangerous_functions` and `db.store_gadget(...)` — neither exists (`Binary` has no such attribute; the DB method is actually `save_gadgets`). Breaks the documented contract new contributors would code against.
- **LOW** — `binary.py` search/strings fallbacks return file offsets, not virtual addresses (inconsistent with the pwntools-backed path); `context.py:from_binary` aliases the same `Protections` object by reference rather than copying; `helpers.py:fit()` always packs as `p64` regardless of target bitness.
- **What's solid:** `database.py`'s SQLite queries are fully parameterized (no SQLi); no `eval`/`exec`/`pickle`/`shell=True`/`os.system` anywhere in this scope; every subprocess call uses argv lists; `protections.py:_get_relro_type`'s actual detection logic is correct (the bug is that other code doesn't use it); `p64/u64/p32/flat` packing helpers and the logging module are clean.

## 2. Vulnerability detection (`vulns/`)

- **CRITICAL — the entire UAF detector is dead code.** `uaf.py` (lines 105, 127, 161, 286, 491): every `UAFVuln(...)` constructor call passes `name=` (not a real dataclass field), omits the required `vuln_type=`, and passes a raw string where a `VulnSeverity` enum is expected. Every call raises `TypeError`, silently swallowed by a broad `except`, so `UAFDetector.detect()` always returns `[]`. **Heap use-after-free detection has 0% recall, silently, right now.**
- **CRITICAL — `heap.py:91-109` and `integer.py:76-96` static detection is hardcoded `return []`.** Heap and integer-overflow vulnerabilities are only ever detected from a supplied crash — never from static analysis of a binary alone. Any such bug that doesn't happen to match a fuzzer-produced crash is invisible to the tool.
- **HIGH — the "100% precision/recall/accuracy" claim in `TEST_RESULTS.md` was measured on `analysis/static.py` (Section 1), not on these `vulns/` detectors**, which are mostly PLT-import-presence heuristics rather than the "disassembly-based" logic the doc's prose implies. Only `format_string.py` genuinely disassembles.
- **HIGH — `stack_bof.py:87-177`** is a pure import-presence heuristic (no size/disassembly analysis): `read`/`recv` flagged whenever the binary lacks canary+PIE, regardless of the actual size argument — exactly the false-positive failure mode the tool's own `TEST_RESULTS.md` flagged as a known limitation and claimed was fixed. Will not generalize past the specific test set it was tuned against.
- **HIGH — `race.py:181-268`** flags HIGH/CRITICAL TOCTOU races purely on co-occurrence of import pairs (e.g. `access`+`execve`) with zero path/dataflow analysis — near-universal false positives on real programs that happen to import both functions safely.
- **HIGH — `off_by_one.py:149-179` `_check_loop_patterns`** counts raw byte values `0x76`/`0x7e` across `.text` and flags "fence-post pattern" past an arbitrary threshold of 10 — those byte values are common in operands/immediates unrelated to JBE/JLE opcodes; this is noise, not signal, on nearly any binary.
- **MEDIUM — `format_string.py`** (the one real disassembler in this scope) has real gaps: linear-sweeps `.text` as one blob (desyncs on data-in-text or misalignment); only handles direct `call imm` to PLT, missing indirect/register calls and PIE thunks (false negatives); the 32-bit constant-format-string check is hardcoded `return False`, flagging every 32-bit printf as unsafe; register tracking uses brittle string munging.
- **LOW/orphaned** — `off_by_one.py:256-317 analyze_function` disassembles then every branch is `pass` (always returns `[]`); broad `except: pass` blocks throughout the package hide real errors, including the UAF `TypeError` above; `heap.py`/`heap_advanced.py`, `integer.py`/`integer_advanced.py`, `race.py`/`race_advanced.py` are duplicate-pair modules (same fragmentation pattern as the engine layer); `__init__.py` even imports `RaceWindow` twice, shadowing `race.py`'s version with `race_advanced.py`'s. None of `UAFDetector`/`OffByOneDetector`/`RaceConditionDetector` are wired into any CLI command.
- **What's solid:** `detector.py` base classes are clean; the previously-documented `OffByOneVuln` dataclass field-ordering bug is genuinely fixed (verified — no non-default-after-default ordering error remains anywhere in `vulns/`); `format_string.py`'s `BlindOffsetFinder` is well-structured; `stack_bof.py`'s crash-based offset finding (when a crash is supplied) is sound.

## 3. ROP & heap exploitation internals (`exploit/rop/`, `exploit/heap/`)

**Correction to an earlier draft finding:** the "28/56 files under `exploit/` have a bare `pass`-body stub" figure is misleading for this scope specifically — an AST scan found **zero** stub function bodies in all `rop/`/`heap/` files. What actually exists is dozens of `except Exception: pass` swallows, which is arguably worse: it produces **broken-but-plausible** chains/payloads that report success rather than an honest failure.

- **HIGH — dirty gadgets accepted as clean.** `gadgets.py:282`'s non-exact match (`search_str in insn_str`) means `find_pop_reg("rdi")` can match `add rsp,8; pop rdi; ret` or `pop rdi; pop rbx; ret` — gadgets with unaccounted side effects. `stack_change`/`regs_modified` are never populated by the ropper/ROPgadget backends (`gadgets.py:206,232`), so chain builders that lay out exactly one stack word per pop will silently desync on any multi-pop or rsp-adjusting gadget.
- **HIGH — no 16-byte stack-alignment enforcement.** `chain.py`'s `call_function`, `_build_execve_manual`, and `build_syscall_chain` emit chains with no alignment padding before entering libc — `movaps`-based SIGSEGV on modern glibc. Only `build_ret2libc_chain` adds a padding `ret`, and does so *unconditionally* rather than computing actual parity, so it can flip alignment the wrong way.
- **HIGH — `_build_execve_manual` sets rdi to a literal `0`** ("cmd address placeholder", `chain.py:243`) — `/bin/sh`'s actual address is never written, so the generated chain calls `execve(NULL, 0, 0)`. Missing-gadget arguments are silently skipped elsewhere (`chain.py:290-294,396-400`) rather than failing the chain. `build_write_chain` (`chain.py:345-372`) always returns `None` — effectively unimplemented despite looking complete.
- **MEDIUM — `ret2csu.py:228-241` gcc10 call-gadget variant is broken.** Moves `r12`(the call target) into `edi` instead of moving the actual first argument (`r15`) into `rdi` — emits a plausible-looking but non-functional chain. (The standard/pre-2.34 variant at lines 234-238 is correct.)
- **MEDIUM — House of Force not version-gated in `heap/techniques.py`** (lines 245-281, 102-105): recommends/emits House of Force for any overflow with no glibc-2.29 top-size-check gate, unlike the *separate* `house_of_force.py`'s `check_feasibility`, which correctly gates it. On 2.29+ glibc this emits a dead technique as if it were usable.
- **MEDIUM — House of Force evil-size offset likely off by 0x10** (`house_of_force.py:131`, `techniques.py:266`): subtracts `2×header_size` from an ambiguous `top_chunk_addr` (chunk header vs. malloc-returned pointer never documented) — the classic formula is `target − top − 0x10`.
- **LOW/MEDIUM — `safe_linking.py` core encrypt/decrypt XOR and version gate are correct**, but `recover_heap_base_from_null:117` mislabels a page-aligned value as `heap_base` (only true if the chunk happens to sit on page 0); `_looks_like_heap_ptr:157`'s second address-range constant is missing a digit (10× too low); `demangle_with_partial_info:144` only brute-forces 12 of ~36 key bits.
- **Roadmap accuracy correction:** `IMPLEMENTATION_PLAN_V2.md §4.1` claims House of Einherjar and House of Lore are "Missing" — both actually exist and are implemented (`house_of_einherjar.py`, 368 LOC; `HouseOfLore` in `house_of_modern.py`). The roadmap also never mentions an entire implemented modern-heap suite (Kiwi/Emma/Banana/Pig/Husk/Botcake in `house_of_modern.py`). Genuinely absent: House of Orange (enum entry only), Roman, Rabbit (docstring mention only, no implementation).
- **What's solid:** the standard-variant `ret2csu` construction; `safe_linking.py`'s XOR + version gate; `unsorted_bin_attack`'s payload offset; tcache/safe-linking version gates in `select_technique`; the ret2reg jmp/call finder's register+type tracking.

## 4. Exploit orchestration & remote (`exploit/` top-level, `remote/`)

*(Excludes the engine-duplication/orphaned-module/verification-fragmentation findings already central to the phased plan — see that document instead.)*

- **HIGH — `remote/leak.py:187-191` misclassifies real libc addresses as "stack".** The 64-bit leak-type heuristic (`addr > 0x7ff000000000`) is wrong for actual libc addresses (e.g. `0x7ffff7a00000` exceeds that threshold) — `find_libc_base()` (gated on `type=="libc"`) never fires. `format_string.py:713-719` classifies the same kind of address correctly, using the right shift (`>>40 == 0x7f`) — the two leak classifiers in the same codebase disagree, and the one on the automated leak path is the broken one.
- **HIGH — `remote/libc_db.py:108` libc.rip query sends the wrong wire format.** Posts `{"symbols": {"puts": 1520}}` (raw int) when the API expects hex strings (`"0x5f0"`) — `exploit/libc_auto.py:269` does this correctly elsewhere in the same codebase. The primary online libc-identification path silently returns no matches. Its declared fallback, `_query_blukat` (`libc_db.py:131-153`), is an unconditional `pass` stub returning `[]`.
- **HIGH — `exploit/offset_finder.py:565-569` conflates crash threshold with return-address offset.** The binary-search's "first input length that crashes" is reported as the RIP offset with `success=True` — these are not the same number in the presence of canaries or partial overwrites. `find_ret_offset`/`QuickExploit.get_payload` treat it as ground truth: a silently wrong payload reported as a success.
- **MEDIUM — `format_string.py:279-314` 64-bit `%n` payload offset computation isn't a fixed point.** Estimates the format string's length once, derives a slot count, then rebuilds with larger `%N$` numbers that can push the string into another 8-byte slot — invalidating the very slot count just computed. No convergence loop. (The library correctly prefers `pwntools_payload`/`fmtstr_payload` where used — this is the manual fallback path's bug.)
- **MEDIUM — `offset_finder.py:433-440` core-dump method grabs an arbitrary core file** (globs `.`/`/tmp` for `core*`, uses whichever sorts first) — a stale or unrelated core produces a bogus offset silently; the method also never configures `ulimit -c`/`core_pattern`, so on most hosts it simply finds nothing and no-ops.
- **MEDIUM — single-send protocol assumption breaks multi-stage/menu-driven targets.** Both `offset_finder.py` and `format_string.py`'s offset-finding send one payload and wait, with no prompt/banner anchoring via `recvuntil` — real targets with a menu or banner before the vulnerable read point get no crash and no offset, a clean-looking but silent failure remotely.
- **MEDIUM — `exploit/ld_preload.py:510-518` `shell=True` with an f-string gcc command.** `output_path`/`output_dir` are interpolated unescaped; the method has no current callers, but it's a public API and any future caller passing a binary-derived `output_name` is a command-injection vector. Also leaks the temp `.c` source file on any compile failure (only unlinked on success).
- **MEDIUM — path traversal + mild SSRF in libc download.** `libc_db.py:262,285` and `libc_auto.py:405,407` build a cache filename directly from the API-returned `libc_id`/`match.id` with no sanitization (`f"libc_{match.id}.so"`) and fetch an API-supplied `download_url` with `requests.get` — a compromised/MITM'd libc.rip response could write outside the cache directory or redirect the fetch internally. Requires API compromise/MITM to exploit; not attacker-binary-controlled.
- **LOW** — `ld_preload.py`'s credential-stealer payload defaults to the predictable, world-readable `/tmp/.creds`; `libc_db.py:468`'s operator-precedence bug (`a and b or c`) can raise `KeyError` mid-parse on certain gadget-listing lines (caught, but truncates parsing); `libc_db.py:614`'s `"libc" in line and ".so" in line` substring check false-matches `libcrypto.so`/`libcap.so` in `/proc/pid/maps`; `remote/interaction.py:303-338 leak_via_puts` has its actual payload-send commented out — it just reads arbitrary data and calls it a leak.
- **What's solid:** `format_string.py`'s `ArbitraryWrite` byte-splitting and `pwntools_payload` delegation; `offset_finder.py`'s `PatternGenerator` (correctly delegates to real pwntools `cyclic`); `remote/interaction.py`'s tube wrapper and bad-character filtering; network calls in `libc_db`/`libc_auto` are uniformly wrapped with timeouts (degrade to empty results rather than crashing — the bug is the *silent empty result* downstream, not an unhandled exception).

## 5. Fuzzing & symbolic execution (`fuzzing/`, `symbolic/`)

**These are not merely unwired — the "smart" pipelines are functionally broken at the algorithm level, independent of any integration work.**

- **CRITICAL — `symbolic/angr_engine.py:244-261` `explore()` never actually explores toward a target.** Builds `find`/`avoid` kwargs but never passes them to an angr Explorer technique; hand-rolls `simgr.step()` with no goal-directed search, then reads `simgr.found`, which is always empty. **`PathFinder.find_path_to_function`/`find_all_dangerous_paths` always return `None`** — the advertised "symbolic execution finds the vulnerable path" workflow does not function at all.
- **CRITICAL — `symbolic/driller.py:193` feeds concrete bytes, not symbolic ones, into angr.** `create_entry_state(stdin=input_data)` passes literal input data rather than a symbolic bitvector — with nothing symbolic, there are no constraints to negate, so hybrid AFL+symbolic drilling never produces new inputs. It's structurally incapable of doing what "Driller" means. `feed_to_afl:326` also writes non-AFL-named files directly into the live `queue/` directory, which AFL won't ingest anyway.
- **HIGH — `symbolic/enhanced_engine.py:288` crashes on its own default arguments.** `args=[self.binary.path.encode()]` — `binary.path` is a `pathlib.Path`, which has no `.encode()` — `AttributeError` on the documented default usage. Also builds its simulation manager without `save_unconstrained=True` (line 323), so `simgr.unconstrained` is never populated and its "unconstrained call" (indirect-jump hijack) detection is permanently dead code. References a `Coverage()` angr technique that doesn't exist in the angr API.
- **HIGH — `fuzzing/cmplog.py:129-132` CMPLOG instrumentation build is a stub.** The actual `subprocess.run` compile calls are commented out; the function returns paths to binaries it never built.
- **HIGH — CLI-level dead ends.** `cli.py`'s `supwngo fuzz --honggfuzz` prints "coming soon" even though a real Honggfuzz wrapper exists elsewhere in the codebase and is simply not wired to this flag; `-j/--cores` is accepted but ignored (no actual parallel fuzzing); `supwngo symbolic` is a silent no-op unless `--find-crashes` is passed, and README-advertised flags (`--find-unconstrained`, `--find-vuln-path`) don't exist as CLI options at all.
- **MEDIUM** — `fuzzing/afl.py:218-220` never emits AFL's `@@` file-input placeholder, so file-input targets (as opposed to stdin) can't be fuzzed at all; hardcodes a 1000ms exec timeout; `symbolic/path_finder.py:144` raises `AttributeError` (`{}` has no `.address`) whenever a requested symbol is absent rather than failing gracefully; `crash_triage.py` always feeds crashes via stdin redirection even for file-input targets (never reproduces file-input crashes) and never sets `access_type="write"`, permanently dead-coding the write-exploitability branch; multiple modules (`afl.py`, `crash_triage.py`, `driller.py`) parse legacy AFL `paths_total`/`paths_found` stats fields that modern AFL++ renamed to `corpus_count` — coverage/stuck-state logic silently reads zero.
- **MEDIUM — `symbolic/constraint.py`** byte-order in `build_overflow_constraints` (claripy `get_byte(0)` is MSB, code treats it as LSB); `minimize_input` unconditionally truncates to 1 byte (a placeholder, not real minimization); `build_format_string_constraints` returns `[]` unconditionally.
- **LOW/resource** — no resource limits on Honggfuzz/LibFuzzer campaigns (no `--rlimit_*`, no run/time cap by default) and no disk-usage cap on crash/corpus growth — a long campaign can fill disk; AFL's hardcoded `-m 200` memory limit is too low for ASAN-instrumented targets and should be `-m none`; `fuzzing/snapshot.py`'s "snapshot fuzzing" is a pure-Python simulation, not real fork/snapshot semantics.
- **What's solid:** `symbolic/constraint.py`'s solver wrapper (`solve`/`solve_n`, printable/alnum helpers, bad-char avoidance) is correct; `fuzzing/libfuzzer.py`'s command construction (artifact_prefix, dict, `-merge=1`, `-minimize_crash`) is faithful to real libFuzzer usage; `fuzzing/afl.py`'s core lifecycle (`get_crashes`/`get_queue`, campaign running, `AFL_NO_UI`, argv hygiene) and `cmplog.py`'s actual `run_afl` invocation (as opposed to its broken `instrument_source`) are correct.

## 7. CLI, tests, packaging

**CLI:**
- Confirmed clean of *other* name collisions (the known duplicate `autopwn` at `cli.py:1015`/`2522`, corrected by peer review to lines 1005/2515, is the only one — all other 30 command names are unique).
- **HIGH — input validation stops at "file exists."** `click.Path(exists=True)` checks existence only, not ELF validity. ~29 of the 31 commands call `Binary.load(binary)` with no surrounding try/except — a non-ELF file produces a raw Python traceback rather than a clean error message. Only `batch`, `cyclic_find`, and `version` handle this gracefully.
- **MEDIUM — inconsistent flag conventions**, directly relevant to designing the goal-2 unified command (this is the anti-pattern to *not* copy): `--output` means a directory in `analyze` but a file in `triage`/`exploit`/`batch`; `-t` is overloaded as `--timeout`, `--technique`, and `--tools` in different commands; `-v` collides between global `--verbose` and `kernel`'s `--vmlinux`; `--libc` has a `-l` short form in four commands but not in the second `autopwn`; `--timeout` type drifts between `int` and `float` across commands; `--json` exists on some commands (`triage`, `batch`) but not comparable peers (`checksec`, `cyclic`, `onegadget`, `libc_id`).

**Tests:**
- **HIGH — tests are overwhelmingly trivial and provide zero coverage of the real pipeline.** `test_core.py`/`test_new_features.py` are dominated by import checks and enum/dataclass round-trips. `AutoLeakFinder`, `ExploitTester`, `Z3ROPSolver`, `LLMVulnAnalyzer` are exercised only with hand-fed parameters or `Mock()` binaries, never through `autopwn`/`EnhancedAutoExploiter` — this independently confirms the "orphaned modules only referenced in isolated tests" finding central to the phased plan.
- **HIGH — the only real-binary tests are dead in the shipped tree.** `test_challenges.py`/`test_all_binaries.py` reference `challenges/` (gitignored, absent) and either `pytest.skip()` immediately or, for `test_all_binaries.py`, aren't even collected by pytest (it lives at repo root, outside `testpaths=["tests"]` in `pyproject.toml`).

**Packaging:**
- **HIGH — `z3` (used by `Z3ROPSolver`) and the LLM SDKs (`anthropic`/`openai`, used by `ai/llm_analyzer.py`) are undeclared runtime dependencies** in both `requirements.txt` and `pyproject.toml`. On a clean install, importing these modules `ImportError`s (silently caught in places, so the feature just vanishes with no explanation).
- **HIGH — `setup.py` and `pyproject.toml` declare genuinely different dependency sets.** `setup.py` dynamically loads `requirements.txt` (which includes `claripy`, `unicorn`, `lief`, `r2pipe`, absent from `pyproject.toml`); `pyproject.toml` hardcodes its own list (including `networkx`, `pyyaml`, absent from `requirements.txt`). Whichever build backend a given install path uses, some declared dependency is silently missing. `setup.py` also folds dev-only tools (`pytest`, `black`, `mypy`) into runtime `install_requires`.
- **MEDIUM — all dependencies are lower-bound-only** (`angr>=9.2.0` etc.), no upper caps — `angr`/`claripy`/`angrop` are notorious for lockstep-versioned breaking changes; an unpinned future `angr` release can silently break the symbolic/ROP paths months after this plan's implementation.

## 8. Security self-audit of the tool itself

Full-repo pattern sweep (subprocess/shell/eval/exec/pickle/SQL/tempfile/SSRF/path-traversal/hardcoded-secrets), each hit manually verified for real data flow (not just a bare grep match). Overall: **cleaner than a typical exploit-dev framework** — no `shell=True` reaching attacker-controlled binary data, no SQLi, no hardcoded secrets, no unsafe `eval`/`exec`. Three real, narrower issues:

- **MEDIUM — insecure deserialization.** `ai/vuln_predictor.py:339` and `ai/pattern_learner.py:152` `pickle.load()` locally-cached model/pattern-DB files with no integrity check. Not currently network-sourced (capping severity), but if either `.pkl` is ever synced/shared/restored from an untrusted source, or the tool is ever used on a shared multi-user host, this is RCE-on-load. Fix: switch to a non-executable serialization format or verify a signature before unpickling.
- **MEDIUM — `exploit/ld_preload.py:510-518` `shell=True` gcc compile with unsanitized `output_name`.** No current callers reach it with attacker-influenced data, but it's exported as public API; any future caller passing a binary-derived name is command injection. (Cross-referenced in Section 4.)
- **LOW/MEDIUM — path traversal via unsanitized libc IDs from network responses**, and a narrow SSRF surface via an API-supplied download URL. (Cross-referenced in Section 4; requires libc.rip API compromise/MITM to exploit.)
- **Verified clean:** all subprocess calls to external tools (gdb/ltrace/strace/ropper/ROPgadget/objdump) use argv lists, never shell strings built from binary-derived data; no `os.system`; no SQL injection (parameterized queries throughout); `tempfile` usage is the safe `NamedTemporaryFile`/`mkstemp` form everywhere except one detection-rule *string* (not an actual call) that happens to contain the word `mktemp`; all outbound HTTP calls set timeouts and don't disable TLS verification outside test code; no hardcoded API keys (read from env only, never logged).

## How this catalog relates to the phased plan

The phased plan (`2026-09-23-effectiveness-and-usability.md`) is scoped tightly to the two stated goals (75% end-to-end success + one unified command) and deliberately does not attempt to fix everything in this catalog — that would be scope creep in the other direction. Read together:

- **Section 0 (import failure)** is now **Phase 0** of the plan — an unconditional prerequisite, added after this catalog and peer review surfaced it.
- **Sections 1, 2, 4 findings that block specific high-frequency techniques** (the broken `cyclic()`, RELRO/FORTIFY misdetection, dead UAF detector, libc leak misclassification, libc.rip wire-format bug, offset_finder's crash-threshold-as-offset bug, ROP alignment/`execve(NULL)` bugs) are exactly the class of fix the plan's **Phase 4/5 (reliability hardening)** is meant to drive — the plan should treat this catalog as its benchmark-failure hit list rather than rediscovering these from scratch.
- **Section 5 (fuzzing/symbolic)** confirms those pipelines need repair, not just CLI wiring, if they're ever revived — currently out of scope for both goals (autopwn doesn't depend on them) and correctly left off the plan's critical path, but should not be marketed as working in README until fixed.
- **Section 6 (module triage)** corrects the plan's "Parked" table: remove `kernel/`, flag `reporting/` as a future wire-in candidate.
- **Section 7 (packaging)** is a blocking dependency-declaration fix folded into the plan's new Phase 0/1.
- **Section 8 (security)** items are low-effort, independent fixes that can land any time; none block the two stated goals but all are worth a small dedicated pass.
- **Section 9 (licensing)** must be resolved before Phase 0's benchmark corpus work, since that phase's approach explicitly reasoned about license terms for what can be committed.
