## 1. The instrument can return a negative verdict

This is reported first on purpose. A scorer that has never failed is not a
scorer, and a low score from an unproven scorer is indistinguishable from a
broken one.

`python3 benchmark/walkthrough/score.py --selftest` — **exit 0**:

| layer | result |
| --- | --- |
| positive control (`good_reference.py`) | **CREDITED** — ran first, as `ablate.py` requires |
| `broken_wrong_offset.py` (offset off by 8) | refused, `NO_FLAG` |
| `broken_undeclared_constant.py` (`NameError` at step 1) | refused, `NO_FLAG` |
| `broken_impossible_route.py` (ret2shellcode on NX) | refused, `NO_FLAG` |
| `broken_launders_flag_file.py` | refused, `FOLLOWER_LAUNDERED` |
| `broken_stale_secret.py` (hardcoded flag) | refused, `NO_FLAG` |
| `broken_scrape_no_target.py` (`cat flag.txt`) | refused, `FOLLOWER_LAUNDERED` |
| `broken_overwrites_target.py` (replaces the staged binary with `cat flag.txt`, runs it, restores the bytes) | refused, `SCORING_WINDOW_TAMPERED` |
| arithmetic truth table (verdicts, denominators, inflation case, gate blockers) | PASS |
| `witness()` vs `witness_argv()` differential | PASS |
| end-to-end, positive control: walkthrough arm solves, bare arm broken | `FOLLOWABLE` |
| end-to-end, necessity: both arms solve | `UNINFORMATIVE` |
| end-to-end, remint: follower hardcodes the flag it was shown | `NOT_FOLLOWABLE`, and the scored secret differed from the one the follower read |
| end-to-end, validity: the bare trial measured nothing | `NOT_MEASURABLE` |

**1 credited, 7/7 refused, 4/4 end-to-end cases correct.** Fixtures are copied to
randomised filenames before scoring, so filename special-casing could not have
produced this. The end-to-end layer drives `run_target` itself with a follower
scripted inside the test, because decoy-then-remint, the per-rep wipe, the
pairing and the asymmetric validity rule live there and the first three layers
never touch them.

### 1c. Two review findings were live false-credit channels, not style

Both found by the independent implementation review
(`docs/plans/reviews/2026-09-24-walkthrough-scorer-implementation-review-codex.md`).

**`attribution.py` counted FAILED `execve` calls as successful target
executions.** This was in the **pre-existing** harness, not in the new scorer.
`parse_trace` accepted an exec event unless the line mentioned `ENOENT` or
`EACCES`, so `E2BIG`, `ENOEXEC`, `EPERM` and `ELOOP` failures each created a
phantom "the target was exec'd" event — the premise the whole lineage rule rests
on. An artifact could force `execve(target, huge_argv)` to fail with `E2BIG` and
then print the flag itself, and every write in that process would be attributed
to the target. Now an allowlist: the syscall result must be exactly `= 0`. The
change can only remove credit, never add it, so no previously reported autopwn
figure is inflated by the fix.

**The staged target is writable by the artifact.** An artifact can overwrite the
binary with `#!/bin/sh\ncat flag.txt`, execute that same pathname, and satisfy
every check — the target was exec'd, the target's tree wrote the flag, nothing
outside the target's lineage opened `flag.txt`. Then restore the bytes so a
content hash afterwards matches. `fixtures/broken_overwrites_target.py` performs
exactly that and is now refused, because `_attest()` pins `st_ino` and
`st_ctime_ns` as well as the hash and `ctime` cannot be forged without root. It
is scored `SCORING_WINDOW_TAMPERED`, which **invalidates** the trial rather than
recording a failure — an "observed failure" in the bare arm is what grants the
walkthrough credit, and the same signature has a benign reading (a walkthrough
that tells the reader to `chmod +x` the binary), so the scorer claims neither.

### 1a. The laundering channel was a real false positive, not a hypothesis

The peer review's sharpest finding. Handing the follower the real `flag.txt`
lets it read the secret and relay it **through** the target, so the *target*
performs the flag-bearing write. Measured directly, with the genuine ret2plt
chain and an `echo` of a Python-read flag:

```
write-attribution verdict : ('credited', "the flag was written by the target's own
                            process tree (dash <- dash <- ret2plt_system <- python3)
                            and the target exec'd a shell")
open-audit hits           : ['python3.11']
```

Write-attribution alone **credits** it. The behavioural open-audit is the only
thing that refuses it. Had the scorer shipped without it, an agent follower could
have scored 100% without exploiting anything, and nothing in the report would
have looked wrong.

### 1b. The walkthrough artifact leaks a path into the corpus

Also measured, not reasoned about. Every generated walkthrough hardcodes

```
BINARY = '<abs path>/benchmark/corpus/02_ret2plt_system/ret2plt_system'
```

which is a signpost to the target's own C source, the manifest and the reference
exploits. The sanitiser rewrote it on the live run (`quoted_paths_rewritten: 1`,
`comment_occurrences_rewritten: 1`) and fails closed if any repository path
survives. Without this, every walkthrough-arm result would have been meaningless.

## 2. Template arm — all 15 round-1 targets, 3 reps

Deterministic executor: runs the walkthrough's own embedded pwntools template.
**This arm has no bare arm, therefore no necessity test, therefore it cannot
produce a followability figure and must never be quoted against the 85% gate.**
It answers one question: does the artifact each walkthrough ships actually work?

Result: **5 TEMPLATE_OK / 8 TEMPLATE_BROKEN of 13 scored; 2 VOID.**

Every verdict was 3/3 or 0/3 — fully deterministic, as expected of this arm. The
arm was re-run unchanged after the `attribution.py` exec-allowlist fix and after
every post-review hardening change, and reproduced the same 15 verdicts
target-for-target — so none of those changes moved a number.

| verdict | targets |
| --- | --- |
| TEMPLATE_OK (5) | `01_shellcode_stack`, `02_ret2plt_system`, `07_ret2libc_leak`, `09_srop`, `15_win_function` |
| TEMPLATE_BROKEN (8) | `03_pie_leak_ret2libc`, `04_canary_leak_bypass`, `05_fmtstr_arbread`, `06_fmtstr_arbwrite`, `08_ret2dlresolve`, `10_int_overflow`, `12_heap_tcache_poison`, `14_negative_index` |
| VOID (2) | `11_heap_uaf_leak`, `13_off_by_one` |

The two VOIDs are exactly the two documented round-1 VOID targets, detected
independently by the same `run_bench.negative_control()` code — `11` by the menu
walk, `13` by the filler blob. That the reused machinery reproduces the known
answer is the best available evidence the reuse is faithful.

### 2a. The failing bucket is two different problems

Worth stating because a single "8 broken" count hides it, and the two need
opposite fixes:

- **7 abstained.** `04`, `05`, `06`, `08`, `10`, `12`, `14` are all
  `family=triage` and end with *"The offset is still unknown; that is the
  blocking fact. Work step 3 (reach the crash)."* — `08_ret2dlresolve`'s version
  of that is an instruction to re-run `supwngo.cli explain … --offset 72`, which
  is the same act: it declines to teach a route it has not determined. That is
  honest abstention — the designed behaviour per the families plan, which makes
  abstention first-class precisely to avoid binary-independent filler. It is an
  engine **coverage gap**, not a route defect. It still captures no flag, so it
  still does not pass.
- **1 taught a route that did not work.** `03_pie_leak_ret2libc`
  (`rop_chain`, *ret2libc via a GOT leak*, confidence 0.6) dies with an
  `EOFError`. That is a **route defect** — the one failure in this bucket that is
  a bug rather than a gap.

(An earlier hand-count in this report's drafting put `08` in the defect bucket.
The figures above are the scorer's own `declared_metadata()` output from the run
recorded here, which is the authoritative reading; the hand-count was wrong.)

The scorer now records each walkthrough's declared family and route, and whether
it declares an unresolved blocker, so this split is visible in every report.
It is **descriptive and affects no rate** — a walkthrough must not be able to
excuse itself by declaring a family that cannot reach a flag.

Note what this means for the R5 gate as currently specified: of 13 scored
round-1 targets, the engine only *attempts* a flag-reaching route on 6, so the
**template** arm cannot approach 85% at this coverage and no scoring choice can
change that.

This is a bound on the template arm **only**. §3b measures the agent follower
credited 2/2 on `12_heap_tcache_poison`, a `hard` target whose template is
`TEMPLATE_BROKEN` — the prose carried a reader past a template that does not run.
Do not read abstention counts as a ceiling on the gate metric.

## 3. Agent arm — the gate metric

Follower tier, pinned: `claude -p`, model alias `sonnet`, CLI 2.1.271, tools
`Bash/Read/Write/Edit/Glob/Grep`, denied `WebFetch/WebSearch/Task`, budget
$2.00, wall timeout 900 s, `--strict-attribution`, variant `verbatim`.
**Stated limitation:** `sonnet` is a mutable alias and cannot be pinned to an
immutable identifier from here.

### 3a. Single-target validation (`02_ret2plt_system`, reps=1)

| arm | outcome | credited | elapsed | blindness hits |
| --- | --- | --- | --- | --- |
| walkthrough | CREDITED | yes | 34.5 s | none |
| bare | CREDITED | yes | 113.6 s | none |

Verdict: **UNINFORMATIVE.** Decoy and scored flags differed in both arms; the
sandbox was wiped between the freeze and the scoring build.

This is the predicted and openly-accepted consequence of a capable follower,
arriving on the very first target measured: a Sonnet-tier agent solves an easy
ret2plt bare, so that target cannot demonstrate the walkthrough contributed
anything. The walkthrough made it **3.3x faster** — a real effect, and one the
gate metric is not designed to capture, because "faster" is not "followable".

### 3b. Hard-tier subset

`benchmark/results_walkthrough/20260924-163832Z/report.json`. Four targets chosen
to be the hardest the corpus offers — one `medium` plus all three `hard` — reps=2,
paired, fixed arm order, no early stopping.

| target | difficulty | template arm | walkthrough k/N | bare k/N | paired w/b/both/neither | verdict |
| --- | --- | --- | --- | --- | --- | --- |
| `04_canary_leak_bypass` | medium | `TEMPLATE_BROKEN` | 2/2 | **2/2** | 0/0/2/0 | `UNINFORMATIVE` |
| `08_ret2dlresolve` | hard | `TEMPLATE_BROKEN` | 2/2 | **2/2** | 0/0/2/0 | `UNINFORMATIVE` |
| `09_srop` | hard | `TEMPLATE_OK` | 2/2 | **2/2** | 0/0/2/0 | `UNINFORMATIVE` |
| `12_heap_tcache_poison` | hard | `TEMPLATE_BROKEN` | 2/2 | 1/2 | 1/0/1/0 | `NOT_MEASURABLE` |

```
eligible 4 | informative 0 | rate_strict 0/4 = 0.0%
rate_informative WITHHELD -- 100% of the eligible set dropped out (ceiling 20%)
GATE: NOT STATED -- subset run; 1 target NOT_MEASURABLE
```

Every credit is a behaviourally attributed flag-bearing write; decoy and scored
secrets differed in all 16 trials.

**Three findings.**

1. **The informative denominator on this subset is 0.** The bare Tier-3 follower,
   given only the binary, captured the flag on **both** `08_ret2dlresolve` and
   `09_srop` at 2/2. These are the corpus's `hard` targets. This is the
   `UNINFORMATIVE` collapse the plan accepted in principle, now measured at the
   top of the difficulty range rather than only on an easy ret2plt — which is
   worse than "a strong follower trims the easy tail".

2. **`12_heap_tcache_poison` is `NOT_MEASURABLE`, and correctly so.** Its rep-1
   bare trial hit the 900 s wall. A timeout is not a failure, and the scorer scored
   it `FOLLOWER_INVALID` rather than letting an unmeasured bare arm read as "the
   bare arm did not solve it" — which would have *granted* the walkthrough a
   `FOLLOWABLE` verdict on missing evidence. The asymmetric validity rule is not
   decoration; it fired on the first hard target that stressed the bare arm.

3. **The agent arm is credited where the template arm is broken.** `12` is `hard`
   and `TEMPLATE_BROKEN` (its own embedded template captured nothing in 3/3 reps),
   yet the agent following that walkthrough was credited 2/2 via a GOT overwrite.
   So `{walkthrough arm succeeds} ⊋ {template arm succeeds}`: a reader repairs a
   broken template from the prose around it. Any estimate of the informative
   denominator drawn from `TEMPLATE_OK` counts is therefore too pessimistic, and
   an earlier draft of the tier-decision document made exactly that error. It is
   corrected and the correction is recorded there, in §2a.

The two targets that carry timings both show a **cost** difference rather than an
outcome difference: 34.5 s vs 113.6 s on `02_ret2plt_system`, and a credited
walkthrough arm against a 900 s bare timeout on `12`. See
`docs/plans/2026-09-24-walkthrough-follower-tier-decision.md` for what follows from
that, the options rejected, and what would flip them.

## 4. What the numbers do and do not license

- **No gate verdict is stated.** Every agent run here was a subset, and the
  scorer emits `gate: null` with the reason rather than a figure that would be
  quoted downstream regardless of the caveat above it.
- **Coverage, not scoring, is the binding constraint on R5.** 7 of 13 round-1
  walkthroughs honestly abstain. The families work in flight
  (`fmtstr`/`integer`/`heap`) is on the critical path for the walkthrough gate,
  exactly as the R5 spec's sequencing says.
- **The `UNINFORMATIVE` problem is real, measured, and not confined to easy
  targets.** It appeared on the first easy target and then on **both** `hard`
  targets at 2/2, at Tier-3 follower capability. Informative denominator on the
  5 targets attempted with the agent follower: **0**. A frontier-tier follower
  would make it worse. The denominator must be stated before measuring, and 15
  must not be assumed — as the R5 spec already says. The scorer now refuses to
  state a gate verdict below `MIN_INFORMATIVE_TARGETS = 7`, because on a smaller
  denominator one target decides the gate; 7 is the smallest n at which it cannot
  (6/7 = 85.7% passes, 5/6 = 83.3% does not).
- **Template coverage does not bound agent-arm coverage.** `12_heap_tcache_poison`
  is `hard` with a broken template and the agent following its walkthrough was
  credited 2/2. "7 of 13 walkthroughs abstain" constrains the template arm only.
- **Isolation is process-level, not OS-level.** `HOME` is shared because the
  follower CLI needs its credentials there, and a follower with a shell can read
  the filesystem. Detected by transcript audit, not prevented. A container is
  the correct fix and is not built.
- **The spec/review conflict on the denominator is surfaced, not resolved.** The
  R5 spec removes `UNINFORMATIVE` from the walkthrough denominator; the reviewer
  showed that lets breakage raise the rate. Both numbers are published,
  `rate_strict` is named gate-safe, and `rate_informative` is withheld as a gate
  result past 20% exclusion. **A maintainer decision is required.**

## 5. Open questions for the maintainer

1. Confirm `rate_strict` (UNINFORMATIVE counted as non-passing) as the R5 gate
   figure, or accept the spec's `rate_informative` with its inflation channel
   documented.
2. Confirm the follower tier and affordance profile for R5. `sonnet` + `shell` is
   the current default and what every figure here used; the choice changes both
   arms and the `UNINFORMATIVE` count, and figures across tiers or profiles are
   not comparable. The argument for keeping the tier, the two options rejected (a
   weaker tier; bounding the bare arm), and the unmeasured symmetric alternative
   (`--affordance read-only`) are in
   `docs/plans/2026-09-24-walkthrough-follower-tier-decision.md`.
3. Decide, **before** R5 is measured, whether a cost/speedup companion measure is
   wanted alongside the pass-rate gate. It is the only proposed measure that
   survives an informative denominator of 0, and the two timed comparisons here
   both show a cost effect. Adopting it *after* seeing a collapsed denominator
   would be indistinguishable from inventing a friendlier metric, so it is raised
   now and not adopted unilaterally.
4. Decide, **before** R5 is measured, whether abstaining families (notably
   detection-only heap) are in the flag-capture denominator or reported against a
   detection-quality criterion instead. The families plan recommends the latter.
5. Whether to fund OS-level follower isolation before R5, given that the current
   guarantee is detection rather than prevention.
